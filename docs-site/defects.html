    Known defects and open questions

    The project's own documents lead with this material, so this page does too. Nothing here is inferred: every item is taken from the M1 gate report, the risk register, the tracker or the source.

    How to read the statuses on this page

    Task statuses were read from docs/tasks.yaml on 2026-08-04, and the working tree was being edited by another session while this page was written. A task can therefore be marked todo in the tracker while code annotated with its id already exists — RL-M1-049 and RL-M1-050 were both in that state when this was written. ./scripts/tasks list --milestone M1 is the current answer; a page is not.

    Outstanding at the M1 gate

    Both M1 exit criteria are met and eleven tasks remain open inside the milestone. The gate report is explicit about the one that could have been quietly closed:

    RL-M1-020 stays in review, honestly

    Its first acceptance line says all four authentication paths are limited. Sign-in and two-factor are; password reset and token exchange have no endpoints yet, so their budgets are published and unspent. Two of four is not four.

    Still todo inside M1

    M1 tasks still todo, with risk and the acceptance that defines them
    TaskRiskWhat it is
    RL-M1-046high Chase the intermittent failure in the no-default-secrets suite. Seen once and not reproduced in 31 runs. Its assertion now names its own cause if it recurs, and the reading that would have made it a product defect is eliminated by a test that generates and validates the secret set 60 times. Acceptance: identify the cause rather than retry the test, establish whether it predates the bootstrap work rather than assuming, and pass fifty consecutive full runs.
    RL-M1-049high Put the CSRF guard in front of every request, not every guarded route. The guard used to live inside the guarded-route loop, so POST /auth/sign-out — bound above it as a public route — never reached it: a cross-origin fetch with credentials from any page an operator visited ended their session, and left no audit entry either. Only SameSite stood in the way, and the CSRF module argues at length that SameSite must never be the only lock. Authorized by the owner under A-03.
    RL-M1-050high Make the audit half of a refusal impossible to drop. A cross-tenant probe on GET /projects/:projectId left no audit record. The fix is in the signature: a refusal cannot yield a wire response without an audit entry that covers it. Authorized by the owner under A-03.
    RL-M1-051medium Fail the coverage gate for an authz file no test ever loads. A file under src/authz/ that nothing imports contributes nothing to the aggregate rather than dragging it down, and a module with no branches must not satisfy the can() branch gate by having nothing to cover.
    RL-M1-052high Catch a repository export that is not async. The repository-gating scan — the durable fix for R-29 — does not currently match a non-async export, so one could slip past the check that every exported repository function resolves a permission.
    RL-M1-053medium Give audit.actor_id referential integrity. An audit entry naming an actor that does not exist should be refused by the database rather than by convention, and the sign-in service identity should exist as a row before it is used as an actor.
    RL-M1-054medium Check the cookie secret for entropy, not just length. A secret that passes the length check while carrying no entropy is currently accepted, and createServer should not be constructible with one.

    Two more items the gate report lists that are not defects in the product: RL-M1-048 — both CI jobs ran the whole suite, so it executed twice per run for one extra file's worth of signal — is now done, and the acceptance was ruled met on the compute figure rather than the wall clock: total CI compute fell from 538 to 181 job-seconds, a 66% cut, while a single pipeline's wall clock fell 21% because the jobs run in parallel and the code job was always the long pole. That ruling is recorded as A-02 rather than by editing the criterion, so the tracker still says “wall clock” and the authorization says why 21% was accepted.

    Four defects that were invisible while every test was green

    All four were found by timing or stress rather than by running the suite.

    1. A scratch-database name derived from a boot-shared clock collided across processes, and with (force) turned that collision into terminated connections mid-test. Two individually correct decisions, jointly a landmine.
    2. Twelve suites passed locally on cluster state an early session left behind. alter role … login is persistent. Only a fresh CI database could notice.
    3. A twenty-fold “regression” reported from one sample, which four timed runs showed did not exist. Both slow measurements had been taken while orphaned processes from the reporter's own killed commands hammered the same database.
    4. ci-metrics reported counts and not names, so the first two CI failures were undiagnosable without local reproduction. It now names failures, capped so a wholesale breakage does not bury the gate.
    The pattern, stated plainly by the gate report

    A test suite measures correctness, not its own health.

    Three mutations also escaped during M1's mutation testing, and each is recorded rather than omitted because each exposed a test asserting the right thing for the wrong reason.

    Open questions the owner holds

    The M1 gate report ends with five requests. None had been answered when this page was written.

    What the M1 gate report asks the owner for
    #The questionWhy it cannot wait indefinitely
    1 Eighteen decision records are proposed and none is accepted. §2.6 reserves acceptance for the owner. Two are named as most wanted: ADR 0016, because it assumes Secure works on http://127.0.0.1 and that could not be verified without a browser, and ADR 0006, because M2 builds on it directly.
    2 R-08 — all three crown-jewel keys live on one machine. M2 hardens around this choice. A ruling now is cheaper than a ruling later.
    3 Is M7 v1 scope or post-v1? Sixteen tasks wait on the answer.
    4 The managed-database scope change itself — Mongo, PostgreSQL and MySQL with database and user creation. It is a real expansion of §5.2, which put managed databases out of scope for v1, and it needs an explicit yes rather than an inference. A-01 covers proceeding through gates on the existing plan, not enlarging it.
    5 Does docs/THREAT-MODEL.md stay public? It names the crown jewels and states plainly that concentrating all three on the control plane is the biggest structural risk in the design. That is what a threat model should do; it is also a roadmap for anyone attacking a real deployment, and the repository is now public.

    Two further open questions sit in the risk register with the owner as owner: R-02 — whether C2's strict reading is intended, which decides whether sites have editable build commands at all — and R-05's policy half, on production and non-production sharing a host.

    docs/PLAN.md §9 also carries six open questions from M0. Two have since closed — the integration host (R-01) and the front-end framework (R-03). Four remain: C2 versus user-authored build commands; SAML, which §6.3 lists but the M5 exit criteria omit and which is tracked as RL-M5-006; per-PR preview environments, allowed by §6.5 “if it doesn't blow the milestone” and tracked as an explicit decision point at RL-M3-027; and managed databases.

    Where the documents disagree

    Reading these files together surfaces places where two of them say different things. None of the following is a security defect; all of them are reasons to prefer a generated file over a written one when the two conflict.

    Discrepancies between documents in the repository
    Subject What each says Which to believe
    Test count .ratline/metrics.json: 422 unit test cases plus 191 in test/authz. docs/gates/M1.md: “598 tests”. README.md: “602 tests passing”. The metrics file. It is rewritten on every run; the other two are prose snapshots taken at different moments.
    M1 task count README.md: “44 of 47 tasks done”. docs/gates/M1.md: “45 of 48 done. Three outstanding”. docs/STATUS.md: 43 done of 54, with 4 in review and 7 todo. The dashboard. Tasks were added to M1 after both prose figures were written, which moves the denominator as well as the numerator.
    Matrix size and bound routes docs/THREAT-MODEL.md R-30: “only 56 of 567 matrix cells”, “the server binds 8 of 27 declared routes”. docs/STATUS.md and the metrics file: 630 cells, 30 declared routes, 12 bound. 630 and 12 of 30, which generateMatrix() and transportCoverage() compute. The M1 gate report already corrected the same two numbers in its own text and explained the mistake — 27 was invented, and “eight” was the count of transport-expressible cells per role (8 × 7 = 56), a different quantity that happened to appear in the same sentence. R-30 was not updated to match.
    How many ungated repository reads docs/gates/M1.md: “nine repository reads that resolved no permission at all”. docs/THREAT-MODEL.md R-29: “Six repository reads resolved no permission at all”, then enumerates seven — listAudit, verifyAuditChain, the two verification reads, and the organization, member and project reads. Unresolved. Three figures appear for one finding, and R-29's own count disagrees with R-29's own list. The fix is not in question — test/security/repository_gating.test.ts now requires every exported repository function to resolve a permission or carry a written argument for why not.
    “There is no action for revoking a member's active sessions” The KNOWN GAPS note at the foot of src/authz/roles.ts says so. The catalogue. member.revoke_sessions exists, is held by Owner and Admin, and POST /members/:userId/revoke-sessions is one of the twelve bound routes. The note was not updated when RL-M1-018 landed.
    Drizzle ADR 0001 names “Drizzle behind a mandatory scoping layer”, docs/PLAN.md §7 says db/internal “constructs the Drizzle client”, and src/db/internal/README.md repeats it. The code. src/db/internal/handle.ts uses pg directly with raw SQL, and drizzle-orm is not a dependency in package.json. C3's three layers hold either way — the change is which library sits behind scoped().
    Where the operation catalogue lives docs/PLAN.md §7 puts it in src/ops/ with generated types in agent/internal/ops/. The tree. src/ops/ holds only a README; the catalogue is src/agent/catalogue.ts and the generated file is agent/internal/protocol/catalogue_gen.go. The behaviour matches the plan; the paths do not.
    The API token ceiling docs/THREAT-MODEL.md R-12: the ceiling “is enforced in RL-M1-032, which has not landed. Until it does, a token's permissions are whatever its grants say.” The code and the tracker. RL-M1-032 is done, and can() evaluates the intersection against the issuing user on every decision, not only at issue time. The register entry is stale.
    Whether an HTTP layer exists docs/THREAT-MODEL.md R-15 says “nothing calls the limiter — there is no HTTP layer”, and R-21 says the address-derivation risk is “owed by whatever builds the HTTP layer”. R-23, in the same table, is marked closed because createServer now runs the CSRF guard on every unsafe method. The server exists — src/api/server.ts, RL-M1-042. R-23 was updated and R-15 and R-21 were not, so the file contradicts itself within one table. The underlying risks are still real: RL-M1-020 remains in review because two of four authentication paths have no endpoint.
    R-17's closing condition R-17 is “Open until two-factor authentication ships (RL-M1-019).” RL-M1-019 is done. The residual R-17 describes — the impersonation window itself — is genuinely not closable, which is what the entry's own body says; only the stated condition is out of date.
    The reserved production hue docs/DESIGN.md §10.1 ends “Owed by RL-M1-027's token work: the reserved hue does not exist yet.” The tokens. RL-M1-040 is done and ENVIRONMENT.production exists in src/web/lib/design/palette.ts, chosen by search over the violet band at 286° against the three requirements the ruling set, with contrast measured rather than asserted.
    Two documents about secret values for Infrastructure Brief §6.3 says Infrastructure “cannot read production secret values”. RL-M1-010's acceptance says “provably cannot read secret values”, with no qualifier. Neither, and the disagreement is flagged in the source rather than resolved silently. src/authz/roles.ts D1 implements the stricter reading and records that the two documents genuinely disagree, noting that the narrower reading is still reachable as an environment-scoped custom role.
    Milestone count Brief §8 defines M0 to M6. docs/milestones.yaml holds M0 to M7. Both, in sequence. M7 is an amendment to §5.2 made by ADR 0013 at the owner's request, and the milestone's own goal field says so. Whether the amendment is accepted is open question 4 above.
