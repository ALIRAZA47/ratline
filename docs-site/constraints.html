ratline / constraints

    The six hard constraints

    These derive from studying how the incumbents fail. The brief calls them requirements rather than preferences: violating one is grounds for rejecting the work regardless of how well it functions. If a constraint blocks the work, the instruction is to stop and escalate, not to work around it.

    Each constraint below carries three things — what it forbids, the specific failure it was written against, and where in this repository it is enforced today. The threat model keeps the same trace on purpose, so that a future session cannot simplify a constraint whose reason has been forgotten.

    C1 — The control plane must never require root SSH to managed hosts

    What it forbids

    An SSH account on a managed host that must be root or in the docker group. Any day-to-day operation that needs privilege by way of a general-purpose remote shell. Privileged operations pass through a narrow, enumerated set of allowed actions with typed arguments, and nothing else.

    The failure it answers

    Coolify's 2025–26 vulnerability class reached CVSS 10.0 specifically because its SSH account must be root or in the docker group. Every command-injection bug therefore became instant host compromise plus container escape. The structural fix is not to be careful with SSH; it is to remove the ability to express an arbitrary command at all.

    How the code enforces it

    Two mechanisms, and the second is the one that makes the first worth having.

    • The catalogue is closed. src/agent/catalogue.ts declares 13 operations and 13 argument kinds. No kind can express a free-form command, and operation() returns null rather than a default, so there is no fall-through branch. The Go side is generated from the same file into agent/internal/protocol/catalogue_gen.go, and CI runs ./scripts/gen-agent-protocol --check so drift fails the build.
    • The agent is unprivileged and the root helper distrusts it. ratline-privd runs as root, socket-activated, with no network access, accepts only the enumerated privileged operations, identifies its caller by SO_PEERCRED, and re-validates every argument independently. That is what makes C1 hold against a compromised agent rather than only against a compromised control plane.
    Built and not built

    The operation catalogue and the signed envelope exist in TypeScript and Go today (src/agent/catalogue.ts, src/agent/envelope.ts, agent/internal/protocol/). ratline-privd is scaffolded as a command (agent/cmd/ratline-privd/main.go) but its socket-activated implementation is RL-M2-008, still todo, as are SSH bootstrap (RL-M2-010) and the check that no root SSH credential remains afterwards (RL-M2-029). C1 is designed and partly built, not yet demonstrated on a host.

    C2 — No shell command is ever constructed by string interpolation

    What it forbids

    All remote execution uses argument vectors with explicit arguments. No sh -c with any user-derived data, anywhere. No template-literal shell construction, however safe the input looks — §9 lists it as automatic rejection.

    The failure it answers

    The same one as C1, one layer down: injection through any user-controllable field that can reach a host. C1 removes the privilege; C2 removes the injection point. Either alone leaves the other doing all the work.

    How the code enforces it

    • The control plane executes no processes at all. eslint.config.js restricts imports of child_process and node:child_process in control plane code, with fixtures at test/fixtures/lint/process_spawning.ts and test/fixtures/lint/shell_template_literal.ts proving the rules fire, checked by test/security/lint_rules.test.ts.
    • The argument vocabulary cannot express a command. There is deliberately no text, string, args, command, flags or env argument kind, and test/security/agent_operation_catalogue.test.ts fails if one appears. Patterns are RE2-compatible so Go and TypeScript cannot diverge on what they accept.
    • Content blobs are inert until a parser vouches for them. A systemd unit or a server block is text, so four kinds carry a named validator — systemd-analyze-verify, nginx-t, visudo-c, x509, pkcs8 — and privd runs the parser and refuses on a non-zero exit before installing anything.
    Open conflict — R-02, owner

    C2 and §6.5 disagree. §6.5 requires configurable build and install commands, which are shell strings by nature (npm ci && npm run build). Under a literal reading of C2 that feature cannot exist. ADR 0005 proposes containment rather than elimination: write the command to a file owned by the site's own Linux user, execute it by argument vector as that user inside a resource-limited transient scope, and make setting it a distinct permission. The conflict is recorded as R-02 and needs a ruling. If the strict reading is intended, RL-M3-004 becomes fixed per-framework pipelines and the product is materially smaller.

    The fuzz corpus over every user-controllable field that reaches a host (RL-M2-027) and the build check that fails on shell construction in the agent (RL-M2-028) are both todo.

    C3 — Authorization is enforced at the data-access layer, not the route layer

    What it forbids

    An unscoped findById anywhere in the codebase. Permission checks in route handlers instead of, or in addition to, the data layer. The brief's wording is precise: make the unscoped variant impossible to call rather than merely discouraged.

    The failure it answers

    The IDOR class that let Coolify users reach other teams' servers. A handler that forgets its check must still return nothing.

    How the code enforces it

    Three layers that each fail closed on their own, described in full on the authorization page:

    1. The raw database handle is unreachable outside src/repo/ — one module constructs the client and exports scoped(), and an ESLint no-restricted-imports group blocks every other importer.
    2. Every repository function takes a branded AuthzContext first. Its constructor is not exported, so there is no literal to write and no default value.
    3. Every tenant-scoped table has row-level security enabled and forced, and the application connects as a role that is neither the table owner nor a superuser.

    The test that makes layer 3 real deletes a repository function's own WHERE clause and asserts the query still returns zero rows (test/security/rls_cross_tenant.test.ts and neighbours). Every isolation test connects as the unprivileged role, because a superuser bypasses policies unconditionally and the tests would otherwise pass while exercising nothing.

    The reading that found nine defects

    §9 forbids a permission check “in addition to” the data layer, so M1 shipped no authorization middleware at all. That reading immediately found nine repository reads that resolved no permission — including the audit log, which every authenticated member of a tenant could read in full. A middleware would have masked all nine and left the repositories exactly as wrong. The full account.

    C4 — No default secrets

    What it forbids

    No default signing key, cookie secret, encryption key or admin password. First run generates them and the application refuses to boot without them.

    The failure it answers

    CloudPanel's CVE-2023-35885 was exactly this: a file manager reachable by forging a cookie signed with the shipped default key, exploited in the wild.

    How the code enforces it

    src/crypto/secrets.ts declares three secrets — cookie, kek (the key-encryption key) and instruction-signing — and states three properties in order of importance: nothing has a default; a secret that exists but is weak, truncated or readable by other users on the host is treated as absent-and-worse and the process refuses to start; values never reach a log, an error message or a JSON serialisation, so refusals name the file and the reason and never the content.

    There is deliberately no admin password in that file. The first owner is created by interactive bootstrap, because generating a default administrator credential is the CloudPanel failure itself. ./scripts/preflight checks a host without starting anything, and test/security/no_default_secrets.test.ts plus the artifact grep in RL-M1-022 back it.

    The rule reaches further than the application's own secrets. Migration 2 creates the ratline_app database role NOLOGIN and passwordless on purpose: a login role with a shipped password is exactly the default credential C4 forbids. That choice is why CI's Postgres service runs with POSTGRES_HOST_AUTH_METHOD: trust rather than giving the role a password the product never uses.

    Two items still open

    RL-M1-054 (todo) — check the cookie secret for entropy, not just length. RL-M1-046 (todo) — one intermittent failure in the no-default-secrets suite, seen once and not reproduced in 31 runs; its assertion now names its own cause if it recurs.

    C5 — The dashboard assumes it is not internet-exposed

    What it forbids

    A public bind as the path of least resistance, and a warning an operator can dismiss. Bind to loopback by default, ship documented VPN, Tailscale and IP-allowlist setup, detect public reachability and show a loud, non-dismissable warning.

    The failure it answers

    Roughly 52,000 Coolify instances were sitting on the public internet in January 2026, and almost none of those operators chose that deliberately.

    How the code enforces it

    The dashboard binds 127.0.0.1:7712. src/config/network.ts classifies the configured bind address locally, with no outbound call, into three exposure levels:

    Bind address classification, from docs/NETWORK.md and src/config/network.ts
    Bind addressLevelBehaviour
    127.0.0.1, ::1containedStarts silently. The default.
    10/8, 172.16/12, 192.168/16, fd00::/8networkStarts silently. LAN or VPN.
    100.64.0.0/10networkStarts silently. Tailscale.
    169.254/16, fe80::/10networkStarts silently. Link-local.
    Any globally routable addressexposedRefuses to start without acknowledgement.
    0.0.0.0, ::exposedRefuses to start without acknowledgement.
    Anything unparseable—Refuses to start. No guessing.

    A wildcard bind is refused even on a host with no public address today, because that is a fact about this afternoon: a DHCP lease, an added interface or a cloud migration exposes it with no further change, and nobody re-reads the boot log afterwards. RATLINE_ALLOW_PUBLIC_BIND=1 permits the bind and does not clear the warning — C5 asks for a warning that cannot be dismissed, and an acknowledgement that silenced it would be a dismissal with extra steps.

    C5 also decides the type. All three faces are self-hosted from vendored packages (src/web/lib/design/fonts.ts) because the dashboard must work on an air-gapped VPN with no external origin reachable, and a font CDN would break exactly when someone needs the tool most.

    Known blind spot — R-11

    Local classification cannot see a NAT port-forward, a cloud load balancer, or a reverse proxy on the same host. A dashboard bound to 127.0.0.1 behind a public nginx is fully reachable and Ratline reports contained. ADR 0011 refuses to fix this with an outbound probe: a probe would phone home from every install, create a fleet-wide correlation point, and fail on exactly the isolated networks C5 exists to protect. Every exposure report therefore carries the caveat in its text, so contained is never presented as verified private.

    C6 — Every privileged action is auditable and attributable

    What it forbids

    An action taken by “the system” with no recorded actor. Automation acts as a named service identity with its own permissions, never anonymously.

    The failure it answers

    Unattributable changes. The control on a high-trust actor is auditability rather than prevention — an Owner can do damage legitimately, so the record has to be trustworthy.

    How the code enforces it

    • Append-only at the database level, not by convention. Migration 6 installs a trigger before update or delete on audit_entries that raises audit_entries is append-only. Each entry chains to its predecessor by hash, with a separate truncation watermark, because a chain cannot detect removal of its own head.
    • No audit write path without an actor (RL-M1-016), covered by test/security/actor_attribution.test.ts.
    • A refusal cannot be obtained without the record of what really happened. refuse() in src/api/refusal.ts returns the wire response and the audit record together. The wire response is a frozen constant and the Refusal type is branded, so no module can hand-roll its own 404 with a helpful message. That is what makes indistinguishability affordable: the operator loses nothing because the whole truth is in the audit log, and only the caller is kept in the dark.
    Two items still open

    RL-M1-050 (todo) — make the audit half of a refusal impossible to drop. A cross-tenant probe left no audit record; the fix is authorized (A-03) and has not landed. RL-M1-053 (todo) — give audit.actor_id referential integrity.
