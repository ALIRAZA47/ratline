ratline / overview

    Ratline

    A single control plane that connects to VPS hosts you already own, provisions a hardened web stack on them, and gives a team a clean interface to deploy static sites, Node.js apps and Bun apps from Git — with role-based access control that holds up, and managed SSH access to the underlying machines.

    Read this first

    The repository is mid-build. M0 (plan) and M1 (control plane skeleton) are closed; M2 (the host agent) is in progress. Nothing on this site describes a feature as working unless a file in the repository shows it working, and every page ends with the files its claims came from.

    What Ratline is

    Ratline sits in the same category as Laravel Forge, Moss.sh and CloudPanel for provisioning and hosting, and Coolify or Dokploy for push-to-deploy. The brief states the difference plainly: two things are differentiators and everything else is table stakes executed well.

    It is aimed at engineering teams of two to twenty running their own infrastructure on Hetzner, DigitalOcean, Vultr or bare metal — competent with Linux, unwilling to hand-write Nginx virtual hosts and systemd units per project. Internal tools, marketing sites and production apps share one fleet, so isolation and permissions matter more than they do for a single developer.

    The design tiebreaker

    When in doubt, favour the team of eight with a production incident at 2am over the solo developer deploying a side project. Density, auditability and blast-radius control beat onboarding smoothness. docs/BRIEF.md §3.3

    The two differentiators

    A privilege architecture that never hands the control plane root

    The agent on each host executes only enumerated operations with typed arguments. No operation carries a shell command. The agent itself runs unprivileged, and a separate root helper re-validates every argument independently rather than trusting it — so the property survives agent compromise, not only control plane compromise.

    The agent protocol · C1

    Authorization enforced at the data-access layer

    Every query is tenant-scoped inside the repository function, the unscoped variant cannot be written, and Postgres row-level security holds independently of application code. A handler that forgets its check still returns nothing.

    The authorization model · C3

    Both differentiators are stated in README.md and derived from the six hard constraints, which the brief calls requirements rather than preferences. Violating one is grounds for rejecting the work regardless of how well it functions.

    In scope for phase 1

    Static sites

    Plain HTML, CSS and JavaScript, plus build-step SPAs and static site generators: Vite, Astro, Next static export, the SvelteKit static adapter, Nuxt generate, Eleventy, Hugo.

    Node.js server apps

    Next.js, Nuxt, Remix / React Router, NestJS, Express, Hono, Fastify.

    Bun apps

    Bun.serve, Elysia, Hono on Bun, and Bun used purely as a build tool for any of the above.

    Runtimes are pinned per site: several Node and Bun versions coexist on one host with no global installs. A runtime upgrade is a deliberate, per-site, rollback-able action.

    Out of scope for v1

    The brief lists these as things to design for and not build: managed databases, email hosting, Docker or container workloads, Python, PHP and Ruby runtimes, multi-region, a template marketplace, billing, and a public API beyond what the interface itself consumes.

    One scope change is pending

    Managed databases were requested after M0 and are planned as M7 under ADR 0013, which amends §5.2. Whether M7 is v1 scope or follows v1 has not been decided. Sixteen tasks wait on that answer. docs/gates/M1.md, docs/RISKS.md R-14

    The brief's own instruction about the seam is worth quoting because it shapes the codebase: if you find yourself building an abstraction so databases can be added later, stop — leave a clean seam and a decision record, not an implementation.

    There is also a hard product boundary. Ratline is not a PaaS and not a hosting business. There is no multi-tenancy across untrusted customers: tenants are teams inside one organization that broadly trust each other but should not have unnecessary access. No Kubernetes. No attempt to abstract away Linux — a competent operator should always be able to SSH in and recognise what Ratline did.

    Vocabulary

    One vocabulary runs across code, interface copy and documentation. The glossary is enforced by review rather than by a tool, and the words it forbids are as load-bearing as the words it defines.

    Glossary terms, from docs/GLOSSARY.md
    TermMeaning
    HostA machine Ratline manages. Never “server” in interface copy, to avoid confusion with the web server.
    SiteA deployable unit — one app or static bundle, one domain set, one systemd unit.
    ReleaseAn immutable timestamped build directory.
    DeploymentThe act of producing and activating a release. “Deploy” is the verb; the noun is “deployment”.
    GrantA role assignment scoped to a node in the hierarchy, optionally time-bound.
    PermissionThe raw capability a role composes. Distinct from a grant, which is the assignment.
    AgentThe Ratline binary running on a host.
    Break-glassEmergency temporary elevation. Temporary Admin, never Owner.
    Control planeThe web application, API, workers and database. Never runs customer workloads. Not “panel”, “backend” or “app”.
    OperationOne entry in the enumerated catalogue the agent will execute, with typed arguments. Not “command”, which implies a shell string.
    EnvelopeA signed, typed, nonce'd, expiring instruction carrying exactly one operation.
    CatalogueThe complete set of operations. Closed by construction.
    Privileged helperratline-privd — the root, socket-activated, network-less process that performs privileged operations and distrusts the agent.
    Scope pathThe materialised Organization → Team → Project → Environment path on a hierarchy node.
    Authorization contextThe branded value carrying actor and tenant, required as the first argument of every repository function.
    PrincipalThe name inside an SSH certificate that a host authorises against, derived from a grant.
    Service identityA named non-human actor with its own permissions. Automation is never anonymous.
    Crown jewelOne of the three keys whose compromise is unrecoverable without rotation: SSH authority, instruction signing, secret wrapping.
    Tension lineThe 2px stateful rule beneath the top bar; the deploy spine on the live deployment screen.
    LashingThe notch marking the active rail item, and a step tick on the deploy spine.
    SessionOne person's authenticated access to one organization. A person in three organizations holds three sessions.
    RotationReplacing a session identifier with a new one and revoking the old, on login and on any privilege change. Never an edit to the existing row.
    EngineAn installed database server on a data host. Not “database”, which is one logical database inside it. M7.
    Data hostA host whose role is running database engines. Sites are refused on one by default. M7.
    LabelThe human-facing name an operator gives a database. Never becomes an identifier. M7.
