ratline / authorization

    The authorization model

    One function answers every authorization question, and it lives at the data layer. The permission catalogue is closed, the seven shipped roles are compositions of raw permissions with nothing structurally privileged about them, and tenant isolation is three mechanisms that each fail closed on their own.

    Actions in the catalogue

    106

    Every one carried by at least one default role, asserted by a test.

    Default roles

    7

    Editable. Custom roles compose the same raw actions.

    Matrix cells

    630

    30 routes × 7 roles × 3 subjects, generated from the route table.

    The permission catalogue

    Every authorization question is “may this actor take this action on this resource”, and every action appears exactly once in src/authz/catalogue.ts. Three consequences follow:

    1. The catalogue is closed. Action is a union of literal names, not string. An undeclared action cannot be named in a call to can() without a deliberate cast, and isAction() rejects it at the runtime boundary where names arrive as data — a request body, a stored custom role, an API token's scope list. Deny-by-default is a property of the type, not a rule people are asked to remember.
    2. An action is the raw capability, not the assignment. The assignment of a role at a scope is a grant; the capability a role composes is a permission.
    3. Splitting an action is a security decision, not a taxonomy exercise.

    The splits the brief names explicitly, all present in the catalogue:

    secret.read_name / secret.read_value

    Most roles need the former and almost none need the latter. Of the seven defaults, only Owner and Admin hold secret.read_value.

    Production versus non-production deployment

    deployment.create_production, deployment.create_nonproduction, deployment.rollback_production, deployment.rollback_nonproduction. Granting one without the other is the most common real request.

    terminal.open

    Its own permission, off by default for every role except Infrastructure. terminal.read_recording is separate again, because a recording contains everything typed and printed in somebody else's session.

    site.build_command.write and site.run_command

    Setting a build command is code execution as the site's Linux user, so it is a distinct grant rather than a side effect of Developer. The one-off command runner is separate again.

    Scope levels run widest first — organization, team, project, environment, resource — and the order is load-bearing: permissions inherit downward, so a grant at one level conveys the action at every level after it. Each entry declares the narrowest level at which it is meaningfully granted, which is what makes the difference visible: organization.delete is organization-only, so no project-scoped grant can ever convey it, while site.read reaches down to a single site.

    The seven default roles

    A role is a named composition of raw actions. Nothing about the defaults is structurally privileged — every list is expressible as toggles in the role editor, and storing an edited or custom role is M5 work.

    Why every role's actions are written out rather than derived

    actions: ALL_ACTIONS would be shorter, correct today, and would quietly destroy the completeness check. If any role holds every action by construction, then “every action is mapped to at least one role” is true of any catalogue — including one with an action nobody thought about — and the test that is supposed to fail can never fail. So the lists are written out, Admin's included, even though Admin is defined as a subtraction. The duplication is the mechanism.

    Admin is Owner minus exactly two actions: organization.delete and organization.transfer_ownership. Billing is the one role that holds no navigation of any kind — §6.3 gives it “no infrastructure visibility whatsoever”, and a test asserts the property (every action it holds has resource === "billing") rather than comparing against a copy of the list, so an action added later cannot pass review by also being added to the expectation.

    The judgement calls, written down

    src/authz/roles.ts records seven deviations so that a reviewer can argue with the rule rather than with ninety individual lines. The four that change what a role can do:

    D1
    Infrastructure and Release Manager hold no secret.read_value at all. §6.3 says Infrastructure “cannot read production secret values” — the narrower wording — while the task's acceptance says “provably cannot read secret values”, with no qualifier. The stricter reading is implemented. The narrower one is still reachable without editing the file, because secret.read_value is environment-scoped: an operator who wants staging values but not production grants a custom role at the staging environment. Flagged because the two documents genuinely disagree.
    D2
    Infrastructure holds terminal.open but not terminal.read_recording. A recording contains everything typed and printed in someone else's session, including anything pasted — the most likely place a role denied secret.read_value would meet one. The action carries no “own session” qualifier, so holding it means reading everyone's. Owner and Admin only.
    D3
    grant.break_glass is held by Infrastructure, Release Manager and Developer, and by nobody else. Break-glass grants temporary Admin, so it defeats every restriction by design; its control is detection, not prevention. The question is only who is trusted to trip the alarm, and the answer is the roles that get paged. Viewer and Billing cannot self-elevate.
    D4
    Viewer holds only actions whose verb begins with read. No mutation of any kind, not even api_token.manage_own. The cost is that a Viewer cannot script against the API; the benefit is that “Viewer changes nothing” is a mechanical property a test can check.
    Known gaps, recorded rather than worked around

    Nothing but deployment is split by environment class. The catalogue splits deployment.create and deployment.rollback into production and non-production, and the argument for it — a project-scoped grant inherits into every environment underneath, so an unqualified action conveys production — applies unchanged to site.restart, site.run_command, secret.create/update/delete, scheduled_job.* and backup.restore, none of which are split. The visible cost is Developer: it cannot restart its own staging app, manage staging secrets or own a staging cron job, because each would arrive with the production equivalent attached.

    terminal.open is not scoped to a site — it is declared at resource scope on a host, and whether the resource is the host or the site decides whether a terminal grant on one site leaks the whole box. M6 has to answer that.

    There is no “read own audit trail”, so every role below Admin is opaque to itself: a Developer cannot see why they were denied.

    One gap note is out of date

    The same list in src/authz/roles.ts ends with “There is no action for revoking a member's active sessions”. There is: member.revoke_sessions is in the catalogue, held by Owner and Admin, and POST /members/:userId/revoke-sessions is one of the twelve bound routes. The note was not updated when RL-M1-018 landed.

    can() — one decision function

    src/authz/can.ts is the only place an authorization question is answered. Every branch in it denies except one: the function has a single path to allowed: true, and everything else, including every error, arrives at a denial. An unmapped action, an unknown scope, a disabled account, a database that will not answer — all deny.

    // The single path to true, written as an equality against one literal rather
// than as a list of denials, so a reason added later denies until someone
// deliberately says otherwise.
return {
  allowed: reason === "granted",
  reason,
  action,
  scopeNodeId: scope.scopeNodeId,
  resourceId: scope.resourceId,
};

    The six steps, in order

    1. An action not in the catalogue is a denial, not an error. A name arriving from a request body, a stored custom role or a token's scope list is untrusted until checked here.
    2. No role carries it. With the built-in roles the completeness test makes this unreachable, but a custom role set can leave an action carried by nobody, and asking the database to decide with an empty role list is a round trip whose answer is already known.
    3. May this actor act at all? One question per request, not one per hierarchy node. A disabled account is the shape a compromised one is put into, so intact grants must not save it.
    4. Does the scope node exist? A node that does not exist and one belonging to another tenant are indistinguishable here, because row-level security means the query cannot see the difference either. That is what makes indistinguishability structural rather than a matching pair of code paths.
    5. Precedence, inheritance and expiry, decided in the database. Three objects, each with one job: live_grants owns the expiry predicate, effective_grants() owns inheritance direction, grant_decision() owns precedence — denies first, then allows, else deny.
    6. An API token holds the intersection of its own grants and its issuing user's current ones. Asked only once the token's own grants have already allowed, so the shape on the page is the shape of the rule: an intersection can only narrow, never widen.

    A denial is then explained with a second query that ignores denies on purpose, so it can only ever explain a decision already taken above and must never decide anything. The distinction matters to whoever reads the audit log, because the remedies differ: one is “ask someone for access”, the other is “someone deliberately took it away”.

    The decision carries a reason because three consumers need it and none can be given a bare boolean: the audit log records why, not just what; the role editor's live preview must explain a denial to whoever is toggling permissions, and must call this same function rather than reimplement it; and an operator at 2am needs to know whether they lack a grant or are being actively denied, because the remedies differ.

    What the module deliberately does not do

    • Cache. Role changes must take effect immediately, including on active sessions. A cache here is the obvious optimisation and would break that requirement silently.
    • Know about routes, HTTP, or the shape of a request.
    • Own precedence, inheritance or expiry. Those live in the database; duplicating them here would give one question two answers.

    Two entry points, and why they differ

    can(action: string) accepts anything, because the name may have come from a request body or a stored custom role — it is untrusted, and step 1 denies what the catalogue does not know. require(action: Action) takes the narrow type, because every caller is the project's own repository code asking for a permission it wrote into the source.

    What the narrow type buys is concrete: an invented permission used to fail closed but silently. requirePermission(ctx, "audit_log.verify", …) — a name written during RL-M1-043 — denied every caller with unknown-action, which reads in the audit log exactly like a legitimate refusal. Nothing was insecure, and nothing would have told anybody the feature was simply dead. It is now a compile error.

    require() also checks re-authentication freshness, after permission. The order is the whole of it: an actor who does not hold the action must be refused as not holding it, never asked to prove a password they would then have proved for nothing — and asking first would turn the control into an oracle, where “you were asked to re-authenticate” means “you hold this permission”.

    Three layers of tenant isolation

    C3 says an unscoped read must be impossible, not merely discouraged. “Impossible to call” rules out the usual answers: a review convention is not impossible, a helper you are supposed to use is not impossible, and even a lint rule is only impossible-in-CI — one eslint-disable away.

    The test that makes layer 3 real takes a repository function, deletes its application-level predicate, runs it with a foreign tenant, and asserts it still returns zero rows. Every isolation test connects as the unprivileged role, because a superuser bypasses policies unconditionally and the tests would otherwise pass while exercising nothing.

    Repository functions return null for both “does not exist” and “exists in another tenant”, because the query cannot see the row and the caller therefore cannot tell the difference. Genuinely cross-tenant work — instance administration, the audit chain verifier — needs an explicitly constructed system context; that list is short, enumerated, individually justified, and a test asserts it does not grow silently.

    Why there is no authorization middleware

    §9 lists as an anti-pattern: “Permission checks in route handlers instead of, or in addition to, the data layer.” The owner ruled on that reading, and M1 shipped with no authorization middleware in the HTTP layer at all. No route handler calls can().

    What that reading found — R-29

    Nine repository reads resolved no permission at all. Among them listAudit, verifyAuditChain, the two verification reads, and the organization, member and project reads. audit_log.read is Owner and Admin only, so every authenticated member of a tenant could read the entire audit log.

    It went unnoticed because C3's three layers all held: an unreachable handle, a branded context and forced row-level security, none of which has an opinion about which member of a tenant is asking. That is the question can() answers, and these functions never asked it. Row-level security still confined all nine to one tenant, so it was a within-tenant privilege gap rather than a cross-tenant one, and nothing called them over HTTP because there was no server — the only reason it was never live.

    A middleware would have masked all nine and left the repositories exactly as wrong. The durable fix is test/security/repository_gating.test.ts: every exported repository function either resolves a permission or carries a written argument for why not. Closed as RL-M1-043.

    Two figures differ between documents and both are in the repository: the M1 gate report says nine ungated reads, and threat-model R-29 says six and then enumerates seven. Both are recorded on the defects page.

    The route table

    §6.3 requires that the matrix be generated from the route table so a new endpoint without matrix coverage fails CI. That sentence forces a shape. If routes are declared by calling a framework, the set of routes is only knowable by running the framework, and the action each one requires is knowable only by reading the handler — so “a new endpoint without coverage fails CI” becomes “someone notices in review”.

    So the route table is data, in src/api/routes.ts, and the HTTP framework binds to it rather than defining it:

    // A route that requires none. `publicReason` is mandatory, so an unguarded
// route is an argued decision rather than a forgotten annotation.
export type PublicRoute = BaseRoute & {
  readonly requires: null;
  readonly publicReason: string;
};

    Three things follow. Every route names the action it requires in the same vocabulary the catalogue uses, so an action outside the catalogue does not typecheck. The matrix generator reads the array, so adding a route adds matrix rows automatically. And a route that genuinely needs no permission has to say why — requires: null with no publicReason does not typecheck.

    Thirty routes are declared. Twelve are bound by src/api/server.ts today; a route with no repository function behind it is deliberately absent rather than stubbed, because a stub answers everybody identically and reports itself as guarded.

    The authorization matrix

    Every role × every endpoint × own-resource / other-tenant-resource / nonexistent-resource. Thirty routes, seven roles, three subjects: 630 cells, all passing, run on every build.

    The third subject is the one usually missed. other-tenant is the IDOR case — a real resource belonging to somebody else, a valid identifier the caller should not reach. nonexistent exists to be compared against it, because §6.3 requires the two to be indistinguishable and that is only checkable if both are generated for every route.

    The expectation for each cell is derived from the route and the role, never recorded by hand. A hand-written expectation would be a second opinion about the permission model, and the whole point is that there is only one. The rule is deliberately short — anything longer would be a reimplementation of can(), and a matrix that reimplements the thing it tests agrees with it by construction, including when both are wrong.

    Three verification layers, reported separately

    How the 630 matrix cells are verified, from .ratline/metrics.json
    LayerCellsWhat it proves
    Transport — a real HTTP request 56 That a bound route actually consults the permission model, over a real request, through the CSRF guard.
    Decision — can() with real grants and RLS 448 That the permission model itself is right, against a real Postgres with row-level security on. Not that a route consults it.
    Declaration — unguarded routes, checked structurally 126 That a route declared public is reachable without a grant. Never counted as a permission check.
    Why one aggregate pass rate would be dishonest

    “630 of 630 cells pass” is true and, on its own, misleading. It would let a reader believe 630 endpoint-level probes ran. What actually ran is 56 real requests, 448 decision-layer checks and 126 structural checks, and those three claims have different strengths. The decision layer proves the permission model; only the transport layer proves that a route consults it.

    Two things are not expressible as a request, which is why the transport number is not simply low effort: a route the server does not bind, and a cross-tenant subject on a route with no identifier in its path — the tenant comes from the session, so a URL cannot name another. 12 of the 30 declared routes are bound, 6 guarded and 6 public, and only 6 of the 24 guarded routes have repository functions behind them.

    The M1 gate report's own recommendation for M2 follows from this: bind more routes before adding features. Every route bound raises real end-to-end coverage, and the matrix already demands it.

    Recorded as R-30 in the threat model — as a number rather than a caveat. The matrix report is written to .ratline/authz-matrix.json on every run, and a missing report means the matrix did not execute: there is no arrangement under which yesterday's green matrix is reported as today's.
