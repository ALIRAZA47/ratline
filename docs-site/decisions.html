    Decision records

    Eighteen records in docs/decisions/. Any choice that would be expensive to reverse gets one: the context that forced it, the options with a one-line security assessment each, the decision, and the consequences — including the new attack surface it introduces.

    Every record is proposed. None is accepted.

    That is deliberate, and it is a rule rather than a backlog. §2.6 of the brief says: “ADRs are proposed by you and accepted by me. Do not mark one accepted yourself.”

    The point survived a later instruction. docs/AUTHORIZATIONS.md A-01 records that the owner removed the milestone-gate approval requirement so the build could proceed without waiting — and that the request to have an agent issue the approvals was refused. The reasoning is recorded verbatim: an approval's whole value is that it is the owner's, and an agent signing one converts the agent's own judgement into a record asserting a human decision. That is worse than no approval, because no approval is merely absent whereas a fabricated one is misleading — and it is misleading in the direction that stops anyone from looking.

    A-01 amends §2.7 (gates), not §2.6 (acceptance). Nothing in the build blocks on the word, so the cost of leaving them proposed is zero and the cost of assuming acceptance would be a design record that lies about its own status.

    The M1 gate report names the two it would most like ruled on: ADR 0016, because it assumes Secure works on http://127.0.0.1 — which could not be verified without a browser and is the riskiest assumption in that design — and ADR 0006, because M2 builds on it directly.

    0001 — Stack choice

    proposed docs/decisions/0001-stack-choice.md

    The question. The brief proposes a stack and explicitly invites disagreement. Four constraints do most of the choosing — C3 requires that an unscoped read be impossible to write, which rules out any ORM whose generated client is the natural thing to reach for; C4 requires a refusal to boot without generated secrets.

    The decision. TypeScript throughout, strict, on Node 22 LTS; Hono for the API; Postgres 16 or later with row-level security; Postgres for the queue; Go static binaries for the agent and the privileged helper; every asset self-hosted with no external origin at runtime. The front end is React, ruled by the owner on 2026-08-02 — the record originally recommended SvelteKit and keeps that recommendation visible rather than rewriting it.

    0002 — Agent transport and authentication

    proposed docs/decisions/0002-agent-transport-and-authentication.md

    The question. Three things have to be answered separately, and conflating them is how this goes wrong: who dials whom, what authenticates the channel, and what authenticates the instruction.

    The decision. Agent-initiated mTLS carrying independently signed instruction envelopes over an enumerated operation catalogue. The agent dials out over HTTP/2 with TLS, mutually authenticated, each host holding its own individually revocable client certificate; no managed host listens on a Ratline port. Every instruction is signed with an Ed25519 key stored separately from the database, and the agent verifies signature, target, expiry and nonce before interpreting any argument. Log chunks are not individually signed — they are data, not instructions — but they are bound to a job identifier and rate limited. Key rotation uses an overlap window so there is never a flag-day. SSH is used exactly once, for bootstrap, with an operator-supplied key that is not retained. The protocol in detail.

    0003 — Tenant scoping and the data-access layer

    proposed docs/decisions/0003-tenant-scoping-and-data-access.md

    The question. C3 is unusually precise: make the unscoped variant impossible to call. That rules out the usual answers — a review convention is not impossible, a helper you are supposed to use is not impossible, and even a lint rule is only impossible-in-CI.

    The decision. Three independent layers, each failing closed on its own: the client is constructed in one import-restricted module that exports only scoped(); every repository function takes a branded AuthzContext whose constructor is not exported; and every tenant-scoped table has row-level security enabled and forced, with the application connecting as a role that is neither the owner nor a superuser. The three layers.

    0004 — Host privilege separation

    proposed docs/decisions/0004-host-privilege-separation.md

    The question. One the brief leaves implicit, and it decides how much C1 is actually worth: what privilege does the agent itself hold? If the agent runs as root, C1 holds against a compromised control plane and collapses against a compromised agent — and the agent is the component that parses untrusted input, runs on every host, and executes user build output.

    The decision. Two components with a trust boundary between them. ratline-agent runs unprivileged and does everything it can without privilege, which is most of the work. ratline-privd runs as root, socket-activated, with no network access, accepts only the enumerated privileged operations, identifies its caller by SO_PEERCRED, and re-validates every argument independently. Duplicating validation is deliberate: if it lived only in the agent, privd would be a confused deputy and the boundary would be decorative. privd writes every operation to a root-owned append-only log before performing it, so an attacker who owns the agent cannot erase the record of what they asked for.

    0005 — Command execution and user-authored build scripts

    proposed docs/decisions/0005-command-execution-and-build-scripts.md

    The question. A genuine conflict in the brief. C2 forbids constructing a shell from user-derived data; §6.5 requires configurable build and install commands, which are shell strings by nature. Under a literal reading of C2 that feature cannot exist.

    The decision. C2 holds absolutely for every command Ratline constructs — the control plane executes no processes at all, the agent and privd use argument vectors only, and every user-controllable field reaching a host is fuzzed from the operation schema. User-authored build commands are contained, not interpolated: the text is written atomically to a file owned by the site's own Linux user, executed as ["/bin/sh", "<system-generated-path>"] where every argument is system-generated, as that site's unprivileged user, inside a transient systemd scope carrying the site's sandboxing and limits. Setting a build command is its own permission, and changing it is audited with before and after values. The property held is not “this cannot run code” but “this cannot escalate”.

    Carried as an open risk, R-02, because the brief's own conflict has not been ruled on.

    0006 — Secrets, envelope encryption and redaction

    proposed docs/decisions/0006-secrets-and-envelope-encryption.md

    The question. Not encryption. The leakage paths: a value has to reach a build environment on a host, which means it exists in plaintext somewhere, and secret.read_value must stay separable from secret.read_name.

    The decision. Each secret value gets a fresh 256-bit data key, is sealed with AEAD under it, and the data key is wrapped by the key-encryption key; the name stays plaintext so secret.read_name needs no unwrapping. The key-encryption key is generated at first run, kept in a file readable only by the control plane user, never in the database and never in a backup that also contains the database, and the application refuses to boot if it is missing or looks like a placeholder. Values reach only the agent on the host that runs the site, over mTLS, written to an environment file with mode 0600 — never into a release directory, a build artifact, or a process argument, because arguments are world-readable in /proc. Redaction is streaming-safe across chunk boundaries, covers base64, URL-encoding and JSON escaping, and refuses very short values at set time rather than redacting ordinary text out of every log.

    0007 — Job queue on Postgres rather than Redis

    proposed docs/decisions/0007-job-queue-on-postgres.md

    The question. The brief suggests a Redis-backed queue and invites disagreement. Every stateful component is something a self-hosting operator installs, patches, monitors, backs up and reasons about during an incident. Does the workload actually need Redis?

    The decision. No. Jobs are rows; claiming uses SELECT … FOR UPDATE SKIP LOCKED with a visibility timeout so a worker that dies releases its job; workers wake on LISTEN/NOTIFY and fall back to polling, so a missed notification delays a job rather than losing it. Enqueue happens in the same transaction as the state change that caused it. Retries back off exponentially into a dead-letter state that surfaces in the interface — §9 forbids silent catch blocks, and a queue that quietly drops jobs is the same anti-pattern wearing a different hat.

    0008 — SSH certificate authority design

    proposed docs/decisions/0008-ssh-certificate-authority.md

    The question. The ordinary failure mode: a contractor leaves, someone removes them in the panel, and their key stays in an authorized_keys file on a host that was unreachable that afternoon. The panel says revoked; the host says welcome.

    The decision. Users upload public keys and Ratline never handles a private one. Certificates default to eight hours, configurable per organization, carrying principals derived from the requester's current grants. Principals are the join between the model and the host — a grant on site marketing-www yields principal rl-marketing-www, and hosts authorise through AuthorizedPrincipalsFile generated by privd from the same grant data the interface renders, so neither holds an independent copy of the policy. A user with no grant receives no certificate rather than one with an empty principal list, because an empty list is easy to mis-handle into meaning “any”. Revocation is three mechanisms together: a short lifetime, a revocation list consulted by sshd, and active session termination. Scoped sudo fragments list fully-qualified commands with no wildcards and must pass visudo -c before installation. The web terminal is its own permission, off by default for every role except Infrastructure, recorded in asciicast format, and the recording is separately permission-gated.

    0009 — Where builds run

    proposed docs/decisions/0009-where-builds-run.md

    The question. The brief does not say, and the answer shapes the agent, the release pipeline, the host stack and the security model. Building on the host that serves production traffic means running user-authored code with an unbounded dependency tree on the machine currently answering requests; building elsewhere means an artifact transfer story, a build fleet, and a way to reproduce each site's runtime somewhere it does not normally exist.

    The decision. Build on the target host, as the site's own unprivileged Linux user, inside a transient systemd scope with explicit limits. Build limits default lower than the site's runtime limits, so a runaway build degrades itself before it degrades the host. Per-host build concurrency is capped, and queued deploys show their position rather than appearing hung. Dependency caches are keyed by lockfile content and runtime version, owned by the site user, and never shared between sites — cross-site cache poisoning is impossible by construction and tested.

    0010 — Web server configuration generation, validation and rollback

    proposed docs/decisions/0010-webserver-config-generation.md

    The question. §6.2's strongest clause is “never leave a host with config that fails validation”, which is about crash-safety rather than error handling. A host that loses power between writing a virtual host file and validating it must come back serving.

    The decision. text/template with a fixed set of escapers chosen per interpolation context and no default passthrough — a template that interpolates a raw value fails the build — with allowlist validation before templating, so escaping is the second line rather than the first. Applying a configuration is a seven-step state machine: stage into the same directory, validate with the server's own validator in a complete config context, snapshot the known-good file, swap by rename(2), reload, verify the server is actually serving, and roll back to the snapshot on failure with the validator's real output. Step six matters more than it looks: a reload can succeed while the server cannot bind a port or read a certificate, and checking the process rather than the exit code is the difference between “we reloaded” and “it works”.

    0011 — Detecting public exposure without phoning home

    proposed docs/decisions/0011-exposure-detection-without-phoning-home.md

    The question. C5 requires detecting public reachability. The obvious implementation is an outbound probe, and it conflicts with two other properties: C5 itself implies isolated networks, where a probe times out, and a self-hosted product that calls home on every install creates a fleet-wide correlation point.

    The decision. Classify locally; never make a network call to determine exposure. Three local inputs — the configured bind address, the addresses actually on the host's interfaces when the bind is a wildcard, and whether the operator has acknowledged a public bind — yield three levels: contained, network, exposed. A wildcard or globally routable bind refuses to start without RATLINE_ALLOW_PUBLIC_BIND=1, and that acknowledgement never silences the warning. The blind spot is stated, not hidden: local classification cannot see a NAT port-forward, a load balancer, or a reverse proxy on the same host, so every report carries the caveat and contained is never read as verified private. Overstating certainty would be worse than the warning being absent, because an operator would stop looking.

    0012 — Grant resolution, the expiry clock, and unconditional owner grants

    proposed docs/decisions/0012-grant-resolution-and-expiry-clock.md

    The question. §6.3 requires time-bound grants whose expiry is enforced server-side rather than by a cleanup job, denies that always win, and permissions that inherit downward. can() is built on whatever this decides, so the interface matters more than the implementation.

    The decision. Three database objects, each with exactly one job: live_grants owns the expiry predicate and nothing else, effective_grants() owns inheritance direction, and grant_decision() owns precedence — denies first, then allows, else deny. Both functions read the view, so no resolution path can skip the expiry filter, and all three are invoker-rights: a SECURITY DEFINER function here would run as the migration role and bypass row-level security entirely, undoing C3's layer 3. A test asserts prosecdef is false, because that mistake is invisible in review. Deny-by-default is the else branch, not an absence. An organization-scope owner grant must be an allow with no expiry, enforced by CHECK. And the creation-time expiry check is expires_at > created_at, not > now(): Postgres refuses non-immutable functions in CHECK, and now() would be wrong regardless, because CHECK is re-validated on update and on restore — so a valid grant would become un-updatable and a dump taken today would refuse to restore tomorrow, purely because time had passed.

    0013 — Managed database engines

    proposed amends brief §5.2 docs/decisions/0013-managed-database-engines.md

    The question. The brief excludes managed databases from v1 and says to leave a clean seam and an ADR rather than an implementation. This is that seam, now requested as real scope. The reason for the original exclusion changes what the product is: every workload Ratline manages today is reconstructible from git, and a database is not.

    The decision. Add M7 after M6, with seven properties. Backup and tested restore land before create-and-delete is exposed — the first thing that works is taking a dump and restoring it into a scratch instance, verified byte-for-byte in CI. Engines install through the enumerated operation catalogue, with a version argument validated against a known set rather than a package name passed through. Databases bind to loopback by default, the same posture as C5. Credentials are generated, never defaulted, envelope-encrypted at rest, and database.read_credentials is distinct from database.read, mirroring the secret name/value split. Restore is the most dangerous action in the product and gets its own permission, its own confirmation naming the target, and an audit entry recorded before it begins. MongoDB is scheduled last and separately — a different auth model, different backup tooling, no meaningful DDL quoting story, and an SSPL licence an operator should be told about rather than have chosen for them. Major-version upgrades are explicitly not in M7: in-place upgrade is where irreversible data loss actually happens.

    0014 — Sessions and password storage

    proposed docs/decisions/0014-sessions-and-password-storage.md

    The question. Four decisions, three of them cheap now and expensive later: how passwords are hashed, whether a session is tenant-scoped, what rotation means, and how expiry works.

    The decision.

    • scrypt from node:crypto at N = 217, r = 8, p = 1, with a 32-byte key and a 16-byte per-password salt. bcrypt caps the password at 72 bytes with a small fixed memory cost; argon2id needs a native dependency, against §6.7's preference for the standard library. Parameters are stored alongside the hash so the choice is revisable without a migration. The implied cost is 128 MiB per hash, stated as a fact about the deployment rather than a footnote, and computed by a function rather than left as arithmetic in a comment.
    • A session belongs to a user within one organization. A session is an act of access, not a person, so a stolen cookie reaches one tenant. It is also structural: scoped() binds exactly one tenant per transaction, so an unscoped session table would need a second data-access primitive — the escape hatch C3 exists to prevent. The stated cost is that three organizations means three sessions, which is acceptable because switching organization is a privilege change and has to rotate anyway.
    • Rotation replaces the row rather than editing it — new identifier, new row, old one revoked and retained with a pointer to its successor. An edited row loses the evidence that a rotation happened, which is the thing an incident review looks for.
    • Expiry is absolute, fixed at creation, never extended on use. A sliding window makes “how long can a stolen cookie live” unanswerable, which is the only question the column exists to answer. Session tokens come from the CSPRNG and are stored only as a hash.

    0015 — Authentication rate limiting

    proposed docs/decisions/0015-authentication-rate-limiting.md

    The question. The sign-in path derives a 128 MiB scrypt hash on every attempt, including for accounts that do not exist — which is correct, because deriving unconditionally is what stops timing revealing whether an account exists. The consequence is that an unauthenticated caller can make the control plane do expensive work for free. The interesting sub-questions are about what happens when the limiter itself is under load.

    The decision. A row per organization, dimension, path and window, upserted — bounded by configuration rather than by traffic. The window is fixed, never extended by later attempts, so it releases on time. The bucket key is a digest of the presented identifier computed before anything is looked up. A store that cannot answer fails closed: a rate limiter that fails open is an availability feature, not a control. Both dimensions — per account and per source address — are counted on every attempt and a refusal by one does not short-circuit the other, because otherwise an attacker would spend one account's budget for free as far as their address was concerned, then move to the next account with a clean address budget.

    0016 — CSRF tokens and the session cookie policy

    proposed docs/decisions/0016-csrf-tokens-and-cookie-policy.md

    The question. The cookie policy is the whole decision, because Ratline's deployment model is unusual. C5 means it is commonly served as plain HTTP on loopback, just as commonly as HTTPS behind a reverse proxy on a real domain, and docs/NETWORK.md recommends a third shape — plain HTTP over Tailscale or WireGuard.

    The decision. The token is derived — HMAC-SHA256(HKDF(cookie secret, "ratline/csrf/v1"), session.id) — so there is no migration, no stored state and no synchronisation to maintain. It travels in a request header (X-Ratline-CSRF), never in a cookie and never in a URL. Secure is on by default and comes off only on an explicit, warned acknowledgement. SameSite=Strict, HttpOnly, Path=/, and the __Host- prefix whenever every declared origin is https. Origin — falling back to Referer — is checked against the declared trusted set by exact match as defence in depth, and an unsafe request carrying neither header is refused: every browser sends Origin on an unsafe method, and a non-browser client should be presenting an API token rather than riding a cookie session, at which point CSRF does not apply to it.

    The gate report flags this as the record it would most like ruled on: it assumes Secure works on http://127.0.0.1, which could not be verified without a browser and is the riskiest assumption in the design. The trade-off is real, because Secure on plain-HTTP loopback is precisely the shape C5 recommends.

    0017 — Session idle timeout

    proposed docs/decisions/0017-session-idle-timeout.md

    The question. ADR 0014 gave sessions an absolute lifetime. Should there also be an idle timeout? What an idle timeout is actually bought for decides everything: not a stolen token — that is what revocation, rotation and the absolute lifetime are for — but one scenario, an operator walking away from an unlocked workstation.

    The decision. No idle timeout in v1. An idle rule measured on last_seen_at records the last request, not the last human: a dashboard polling for deploy status writes it on a timer, so the rule would fire only when the tab is closed — which the absolute lifetime already covers — and never for the abandoned open tab, which is the entire scenario. Instead: keep the absolute eight-hour lifetime and make it configurable per organization through the security policy that already exists; require re-authentication for the highest-risk actions, which polling does not defeat and which binds the check to the moment of danger rather than to a clock; and say plainly in the interface that Ratline does not sign an idle session out, so nobody assumes otherwise. Shipping the timeout would be worse than its absence, because an operator who believes the console signs itself out locks their screen less often.

    0018 — Two-factor authentication

    proposed docs/decisions/0018-two-factor-authentication.md

    The question. §6.3 requires two-factor authentication with an organization-level policy, and the task adds three specifics: TOTP enrolment producing recovery codes, an organization able to require it with non-compliant members forced into enrolment at next login, and single-use recovery codes whose consumption is audited.

    The decision. A challenge rather than a partial session, so nothing that has not presented both factors is a session at all. TOTP, with the WebAuthn gap recorded rather than papered over — a shared secret is a symmetric credential the verifier can impersonate its holder with, which is R-25. Secrets are envelope-encrypted with the shape enforced in the database, recovery codes are digest-hashed and single-use, replay protection is monotonic, and no new dependency was added.
