ratline / agent protocol

    The agent protocol

    The control plane cannot ask a host to run a command, because there is no way to say one. It can only name an operation from a closed catalogue and supply arguments that fit a vocabulary in which no free-form command is expressible. The envelope carrying that request is signed, addressed, expiring and single-use, and the order the agent checks those properties in is itself a security property.

    Operations

    13

    10 performed by the root helper, 3 by the unprivileged agent.

    Argument kinds

    13

    Constrained identifiers, bounded numbers, enumerations, validated blobs.

    Kinds that can carry a command

    The signed instruction envelope

    Every instruction is one envelope carrying exactly one operation:

    {
  "operation":      "service.control",
  "arguments":      { "service": "rl-marketing-www", "action": "reload" },
  "nonce":          "<32 random bytes, hex>",
  "issued_at":      1754308800000,
  "expires_at":     1754309100000,
  "target_host_id": "<this host>",
  "signature":      "<Ed25519 over canonicalBytes, base64>",
  "key_id":         "<which key signed — a hint, never trusted>"
}
    Signature
    Ed25519, using the control plane's instruction key, which is stored as a file outside the database.
    Nonce
    32 random bytes, hex encoded. The wire form is therefore 64 characters, and the agent refuses anything else as malformed.
    Validity window
    At most 5 minutes, enforced on both sides. A short window is what makes the nonce store bounded: the agent only has to remember a nonce until it expires, so the store's size is a function of the instruction rate within one window rather than of uptime.
    Future skew
    An issue stamp may sit at most 30 seconds ahead of the agent's local time. Not zero, because clocks differ and refusing every instruction from a host whose NTP drifted by a second would be worse than useless. Not large, because the issue-to-expiry window is what a replay has to land in.
    key_id
    Present so an agent holding two keys during a rotation overlap knows which to try first, and so a rotation that goes wrong names the key rather than reporting “bad signature” for everything. It is not trusted: the agent tries every key it accepts regardless, because a hint an attacker controls must not be allowed to select the verification key — naming a revoked key would otherwise be enough to have it used.

    An agent that holds no accepted keys refuses everything rather than accepting everything. That is written as its own branch, because a range over an empty key list falls straight through to “no key matched”, and relying on that is relying on a coincidence.

    The signature is not over the JSON

    JSON is not a canonical encoding. Key order, whitespace, \/ escaping, unicode escape form and number formatting all vary between implementations, and two of them signing “the same object” produce different bytes. Every protocol that has tried to fix this with a canonical-JSON profile has produced a second specification to disagree about.

    So the signature covers a length-prefixed binary encoding with one legal form per instruction. JSON remains the transport, and the agent re-derives the canonical bytes from the fields it parsed before verifying — so a JSON quirk cannot survive: any encoding difference lands as a signature mismatch, which is a refusal rather than a divergence.

    Why every field is length-prefixed

    Concatenation without lengths is ambiguous, and ambiguity in signed bytes is forgery. {a: "bc"} and {ab: "c"} both flatten to abc: one signature would be valid for two different instructions. Length prefixes make the encoding injective, which is the property a signature needs and the one easiest to lose by accident.

    Why there is a domain-separation prefix

    The same key must never produce a signature valid in two contexts. Without a prefix, an agent's signed response could be replayed as an instruction if the field layouts ever coincided — and “ever coincided” is a property of future code, not of this file. ratline-instruction-v1 names the context and the version, so a v2 envelope cannot be verified as a v1 one either. It is written first and NUL-terminated, so the separator cannot be confused with the start of a field.

    Arguments are sorted by name before encoding, by code unit rather than by locale. localeCompare would make the encoding depend on the machine's locale, which shows up as an unverifiable instruction on one host and works everywhere else. The Go side sorts byte-wise to match.

    The two implementations are independent — src/agent/envelope.ts and agent/internal/protocol/envelope.go — and are checked against each other by committed test vectors rather than by inspection, because “these two functions agree” is not a property source review establishes. scripts/gen-envelope-vectors.ts produces them.

    The verification order is the security property

    Every step before the argument check exists so that an unauthenticated party cannot reach the argument parsers at all. The order is asserted by a test that reads the source file, not merely written down in it — comments do not hold an order in place across a refactor.

    Two further properties of that path are worth naming. A nonce store that cannot answer means replay cannot be ruled out, so the envelope is refused — failing open there would make the whole check advisory the first time a disk filled. And the JSON decoder accepts exactly one value: trailing data would otherwise be ignored, and an envelope followed by a second one is a request to interpret two things while verifying one.

    The operation catalogue

    Thirteen operations. performer carries the privilege, and the boundary is declared in the data so a reviewer can count the privileged operations without reading any implementation — and so the agent can refuse to attempt one itself, up front. Attempting it would fail on file permissions somewhere deep in the work, and a permissions failure is indistinguishable from a misconfigured host, so the operator would be sent to look at ownership instead of at the instruction that should never have been routed there.

    Idempotence is declared per operation rather than assumed of the runner, because M2's exit criteria include “the same action runs twice in a row idempotently”. Declaring it in the data means the harness can drive every operation twice and assert the second run changed nothing, instead of consulting a hand-maintained list. Two operations answer no, and the comments say why: site.user.remove because removing an absent user is a no-op but not the same as the first run, which had something to remove; and service.control because start-then-start is a no-op while restart-then-restart genuinely restarts twice — declared false rather than per-action, because the harness asks per operation and a half-true answer is worse than a false one.

    The argument-kind vocabulary

    “No operation accepts a free-form command” is not achieved by reviewing the operation list. A string argument called options is a free-form command with better manners. It is achieved by there being no argument kind capable of expressing one: every kind is a constrained identifier with an anchored pattern, a bounded number, an enumeration, or a content blob that a named parser must accept before anything installs it.

    Four details in that table that carry more than they look

    service_id
    The rl- prefix is load-bearing rather than cosmetic. It is what stops any operation from naming a unit outside Ratline's namespace, so an instruction can never stop sshd.
    RE2 patterns
    Go's regexp package is RE2, which has no lookahead and no backreferences. A pattern using either would work in the control plane and fail to compile in the agent, so the agent would either refuse everything or — worse, depending on how the error were handled — check nothing. The test suite rejects both constructs rather than trusting a reviewer to notice.
    path_in_site
    A dot may appear only between word characters within a segment, which admits posts/index.html while refusing .hidden, .., a/../b and index..html — without a lookahead Go could not compile. The first version excluded dots entirely and therefore refused every filename with an extension. It was caught by the one test asserting a well-formed instruction is accepted, which exists because a validator failing closed on everything looks identical to a validator working until somebody tries to use it. privd re-resolves the result and re-confirms it is inside the site root regardless, because a pattern is not a filesystem and a symlink is not a path.
    Length before pattern
    The length check runs first in both validators, deliberately, so a multi-megabyte value is refused on sight rather than carried into a comparison. An enumeration makes that comparison cheap, but cheap is not the same as not performed.

    One contract, three checkers

    The catalogue's data is generated in one direction: TypeScript is the source, and ./scripts/gen-agent-protocol writes agent/internal/protocol/catalogue_gen.go. CI runs it with --check, so drift fails the build rather than being promised against in a comment. The direction is not preference: the control plane needs the catalogue's shape available to the type checker at every call site that builds an instruction, and going the other way would lose the literal-union narrowing that makes an unknown operation name a compile error rather than a runtime one.

    The validation is not generated. Three parties check the same contract, and each must do its own checking:

    1. The control plane validates an instruction before signing it. That proves nothing to the agent — but it is still the right place for the error to surface, because a bug here should fail in the control plane's tests rather than as a refusal on somebody's host that looks like a protocol problem.
    2. The agent re-validates, because it must assume the control plane is compromised. Checking code it inherited from the control plane would be checking nothing.
    3. privd re-validates again, because it must assume the agent is.

    Duplicating validation is deliberate: if it lived only in the agent, privd would be a confused deputy and the boundary would be decorative. Generation is what keeps the three from disagreeing about what to check while each still does the checking. The control plane's checks are also not looser than the agent's — a control plane that accepted more would sign instructions that are refused on arrival, and the operator would see a host that rejects valid work.

    The privileged helper

    ratline-privd runs as root, socket-activated, with no network access at all, and holds nothing persistent. It accepts only the enumerated privileged operations:

    • create or remove a site's Linux user;
    • install a validated systemd unit and reload the manager;
    • install a validated web server configuration and reload it;
    • install a sudoers.d fragment, after visudo -c passes;
    • install a certificate and key with correct ownership and mode;
    • install a package from the distribution's repositories;
    • start, stop or restart a service named by identifier in the Ratline namespace.

    It identifies its caller by SO_PEERCRED rather than trusting the socket's mode alone, and re-validates every argument independently of the agent: site slugs re-checked against the strict pattern, paths re-resolved and re-confirmed inside the site root, unit and configuration files re-parsed before install, service identifiers checked against the naming convention so no unit outside it can be touched.

    It also writes every operation to a local append-only log before performing it, owned by root and not writable by the agent user, and ships that log to the control plane audit trail. So an attacker who owns the agent cannot erase the record of what they asked for.

    What exists on disk today

    The catalogue (RL-M2-002) and the signed envelope (RL-M2-003) are done, in both languages, with committed vectors. agent/cmd/ratline-privd/main.go exists as a command entry point; the socket-activated helper itself is RL-M2-008 and its root-owned append-only log is RL-M2-009, both todo. The durable nonce store is RL-M2-007, also todo — the in-memory store lives in agent/internal/protocol/nonces.go. Read from docs/tasks.yaml on 2026-08-04.

    The friction of adding an operation is the feature. It costs a catalogue entry, generated types on both sides, argument validators in the agent and independently in the privileged helper, and fuzz coverage.
