    Roadmap and status

    Eight milestones, 181 tasks. Each milestone's exit criteria are marked met only when a human has seen the criterion demonstrated, not when a task closes — docs/milestones.yaml says so in a comment and maintains exit_met by hand for exactly that reason.

    M0 — Plan

    26 of 26 tasks done · 0 of 4 exit criteria met

    Goal. Technical plan, stack decision with reasoning, data model, trust-boundary diagram, threat model v1, design plan, and the complete tracking system with the backlog populated through at least M3. No application code.

    • ▲ The plan is approved
    • ▲ ADR 0001 (stack) is accepted
    • ▲ ADR 0002 (agent transport) is accepted
    • ▲ The backlog is approved

    All four require the owner's decision, and none has been given, so M0's work is complete while its exit criteria are not met. Nothing was self-accepted. The later authorization (A-01) removed the requirement to wait at a gate; it did not grant approval retrospectively, and it explicitly does not cover ADR acceptance.

    M0's backlog held 143 work items at the gate; it now holds 181, the difference being tasks discovered during M1 and the sixteen M7 tasks added with ADR 0013.

    M1 — Control plane skeleton

    43 of 54 tasks done · 2 of 2 exit criteria met · 6 open high-risk

    Goal. Auth, the organization / team / project model, can() with 100% branch coverage, a hash-chained audit log, a UI shell with the design system applied, and the tracking CLI wired into CI.

    • ● The authorization matrix test harness exists and runs, even though most endpoints do not exist yet — met. 630 cells run every build.
    • ● tasks validate gates the build — met. The tracker job has already failed the build on a stale STATUS.md, which is the check working on its own author rather than on somebody else.

    The gate report is candid about what “done” covers. Both criteria are met, and eleven tasks remain open inside the milestone: four in review and seven todo. Two of the seven are security fixes the owner authorized (A-03) and that had not landed at the time of writing. The full list, with what each one is.

    M2 — Agent and first host

    2 of 29 tasks done at the last render · 0 of 3 exit criteria met · 19 open high-risk

    Goal. The agent binary, SSH bootstrap, host inventory and health reporting, web server and runtime provisioning, and configuration generation with validation and rollback.

    • ◐ A clean Debian 12 host goes from bare to fully provisioned in one action
    • ◐ The same action runs twice in a row idempotently
    • ◐ Zero root SSH after bootstrap

    What exists: the agent scaffold as a dependency-free static binary for two architectures (RL-M2-001), the enumerated operation catalogue shared by both sides with a CI drift check (RL-M2-002), and the signed instruction envelope with committed cross-language vectors (RL-M2-003).

    What does not: the privileged helper itself (RL-M2-008), its root-owned append-only log (RL-M2-009), the durable nonce store (RL-M2-007), agent enrolment and mutual transport authentication (RL-M2-005), SSH bootstrap (RL-M2-010), provisioning, the firewall, the fuzz corpus (RL-M2-027), the shell-construction build check (RL-M2-028), and the integration harness against real hosts (RL-M2-024) — which is owned by human and blocks three other tasks.

    The gate report's recommended scope adjustment for M2 is not a feature: bind more routes before adding features. Transport coverage is 56 of 630 matrix cells because only 6 of the 24 guarded routes have repository functions behind them, and every route bound raises real end-to-end coverage.

    M3 — Static sites end to end

    0 of 27 tasks done · 18 open high-risk

    Goal. Git connect, build pipeline, atomic release, TLS, custom domains, live log streaming, rollback.

    • A real static site deploys from a real repository
    • The site gets a real certificate
    • Rollback completes in under one second

    M3 is where the §2.10 stop conditions bite. A-01 explicitly preserves them: “a missing credential, host or domain still stops the work”. M3 needs a real domain and a real git repository to deploy from, and the agent is instructed to stop and ask rather than invent either.

    M4 — Node and Bun apps

    0 of 15 tasks done · 10 open high-risk

    Goal. systemd unit generation with sandboxing, process management, zero-downtime reload, environment variables with redaction, health checks.

    • A Next.js app deploys and serves traffic
    • A Bun/Elysia app deploys and serves traffic
    • A failed-health-check deploy causes no downtime
    • Both apps honour their configured resource limits

    M5 — RBAC completion

    0 of 7 tasks done · 6 open high-risk

    Goal. The full role set, custom roles, time-bound grants, break-glass, the role editor interface, and the exhaustive authorization matrix.

    • The authorization matrix passes at 100%
    • Every endpoint is covered by the matrix
    • Cross-tenant probing returns indistinguishable responses for unauthorized and nonexistent

    The first two are already true of the 30 declared routes — the matrix passes 630 of 630 and covers every declared route — but the criterion is about endpoints that exist, and most do not yet. The role editor's live preview must call can() rather than reimplement it, and RL-M5-004 tests that parity explicitly, because a preview that disagrees with enforcement is worse than no preview.

    M6 — SSH access

    0 of 7 tasks done · 7 open high-risk — every task in the milestone

    Goal. The certificate authority, short-lived certificates, principals, scoped sudo, and a web terminal with session recording.

    • Revoking a grant kills an active session within the certificate TTL
    • Revoking a grant immediately blocks new sessions
    • A developer with access to one site provably cannot reach another

    M6 also has to answer a question the role definitions could not: terminal.open is declared at resource scope on a host, and whether the resource in question is the host or the site decides whether a terminal grant on one site leaks the whole box.

    M7 — Managed databases

    0 of 16 tasks done · 15 open high-risk · scope not decided

    Goal. Install PostgreSQL, MySQL and MongoDB on managed hosts, create databases and users, and wire credentials into sites. Requested as a scope change to brief §5.2, which lists managed databases as out of scope for v1.

    • A database is backed up and restored byte-for-byte into a scratch instance, in CI, before create and delete are exposed
    • PostgreSQL and MySQL install, create a database and a least-privilege user, and serve a real site
    • No engine listens beyond loopback without an explicit acknowledgement
    • A fuzz test over every label reaching a DDL statement cannot escape the identifier
    • Restore is its own permission and is audited before it begins, not after it succeeds
    • MongoDB is deliberately deferred within the milestone and its licence is surfaced to the operator

    Whether M7 is v1 scope or follows v1 has not been decided, and A-01 does not cover it: that authorization allows proceeding through gates on the existing plan and is explicitly not a blanket yes to enlarging it. Sixteen tasks wait on the answer, and R-14 — the highest-impact entry in the risk register — is the reason the ordering above puts verified restore first.

    How gates work now

    Brief §2.7 required stopping at every milestone gate for explicit approval. A-01, recorded verbatim on 2026-08-04, amends that for the run to a first complete iteration: gate reports are still written in chat and committed to docs/gates/, but the agent proceeds without waiting.

    What stands in for the human review is an adversarial compliance reviewer whose job is to falsify the agent's claims about its own work. It can report a gate unsound; it cannot approve one. It has already earned its place: it caught the transport-coverage paragraph in the M1 gate report, where both numbers were wrong — one invented, and one a different quantity that happened to appear in the same sentence.
