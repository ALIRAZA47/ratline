ratline / threat model

    Threat model and risks

    Ratline manages hosts an organization already owns. There is no multi-tenancy across untrusted customers, and that shapes what counts as a finding: a Developer reaching production secrets is a serious defect; a Developer being able to see that a production project exists is not.

    Assumed out of scope for v1: physical access to hosts, a malicious Linux distribution package, a compromised Git provider, and a hostile hypervisor.

    A tradeoff the project raised about this document

    The M1 gate report carries a candour warning about its own threat model: docs/THREAT-MODEL.md names the crown jewels and states plainly that concentrating all three on the control plane is the biggest structural risk in the design. That is what a threat model should do. It is also a roadmap for anyone attacking a real deployment, and the repository is now public. Whether it stays public is one of the five things the gate report asks the owner to rule on, and it has not been ruled on.

    Assets 1 to 3 are the crown jewels and all live on the control plane. That concentration is the single biggest structural risk in the design, and it is carried as R-08 with the owner as its owner.

    Compromise scenario 1 — a compromised agent

    An attacker fully controls ratline-agent on one host, as the unprivileged ratline-agent user.

    They can

    • read and write inside site directories that agent manages;
    • read the active secret values for sites on that host — it writes the environment files;
    • lie to the control plane about that host's inventory and health;
    • request catalogued privileged operations for that host, which privd performs if the arguments validate: create a site user, install a validated unit or virtual host, restart a Ratline-namespaced service;
    • disrupt service on that host.

    They cannot

    • obtain arbitrary root — privd accepts only enumerated operations, re-validates every argument independently, and identifies its caller by peer credentials;
    • touch units, files or services outside the Ratline namespace;
    • reach any other host — no lateral network path, and the client certificate authenticates one host only;
    • forge an instruction — they hold no signing key;
    • read the control plane database;
    • erase their tracks — privd writes its own root-owned append-only log before acting, and ships it.
    Residual — R-07

    Secrets for sites on that host are exposed. That is inherent: a process running the site must have its environment. The mitigation is blast-radius limitation (per-host, per-site) and detection, not prevention — and detection is currently weak. A compromised agent reporting plausible-but-false inventory would not be caught. Nothing cross-checks an agent's claims about its own host in v1.

    Compromise scenario 2 — a compromised control plane

    They can issue any catalogued operation to every host in the fleet; unwrap every secret; mint SSH certificates with any principals, which is a shell as any site user on any host; read and write all data; issue and forge sessions. Because they hold the signing key, agents will obey them — correctly, since from the agent's perspective these are legitimate instructions.

    They cannot — and this is the C1 payoff — run an arbitrary command on a host directly. The catalogue is closed. They can, however, create a site with a chosen build command and deploy it, which yields code execution as that site's user. So control plane compromise means unprivileged code execution fleet-wide plus a shell via the certificate authority, not instant root.

    The threat model then says something most documents of its kind would leave out: with the SSH authority key in hand, the distinction narrows considerably. Root still requires a local privilege escalation from a site user, which is a real barrier but not one to lean on.

    Compromise scenario 3 — a compromised low-privilege account

    A Developer's account or session is taken over. They can deploy to non-production; read logs, redacted; see secret names; manage their own SSH keys; see project and site structure. They cannot read secret values, deploy to production, change host configuration, open a web terminal, or reach another tenant's resources.

    The sharpest finding in the model — R-05

    The real risk is lateral. If a Developer can set a build command on a non-production site, they get code execution as that site's Linux user. If that host also runs production sites, they are then one sandbox escape away from production data — and the sandbox is Linux users plus systemd, not a namespace, because containers are out of scope for v1.

    Controls: site.build_command.write is a distinct permission, so this is an explicit grant rather than a side effect of Developer; per-site users and directory modes; systemd sandboxing; and an adversarial escape test (RL-M3-006, todo). The structural mitigation is not to co-locate production and non-production sites. The interface should warn when an operator does, and the documentation should recommend against it. Not eliminable within v1 scope.

    Crown-jewel key handling

    How each crown-jewel key is generated, stored, rotated and recovered
    SSH authority key Instruction signing key Secret-wrapping key
    GeneratedFirst use of SSH featuresFirst runFirst run
    StoredFile, control plane, restrictive mode, outside the databaseSameSame
    In backupsExcluded from database backupsExcludedExcluded
    RotationNew authority, distribute, remove old, revoke outstandingOverlap window — agents accept bothRewrap data keys only
    If compromisedSee belowRotate; audit every instruction in the windowRotate; treat every secret as disclosed and force rotation of all of them

    SSH authority compromise recovery. Generate a new authority. Distribute the new trusted-authority file to every host. Remove the old authority. Revoke every outstanding certificate. Any host unreachable during this process still trusts the compromised authority — which is why the procedure must be exercised, and why the set of unreachable hosts must be reported loudly rather than skipped over. Carried as R-06.

    Risk register

    Two files hold risks and they hold different ones. docs/RISKS.md is the live register for planning risks and blocked tasks, and carries owners. docs/THREAT-MODEL.md §8 lists residual security risks that are accepted rather than fixed. Both are reproduced below, merged and marked with which file each came from.

    Owner human means it needs a decision or a resource the agent cannot create. Those are repeated in the gate report under “what I need from you”.

    The merged risk register from docs/RISKS.md and docs/THREAT-MODEL.md §8
    ID Risk Status Owner Where it stands
    R-01 No integration test host ● closed 2026-08-03 human Closed on evidence, not on the offer. ./scripts/host start && verify brings up a Debian 12.15 container and asserts three things: SSH accepts deployer at uid 1000, non-root, with working sudo -n; systemctl is-system-running returns running with systemd 252 as PID 1 and five active socket units; and root SSH is refused by the image's default rather than by a test arranging it.
    R-02 C2 versus user-authored build commands ✕ open human The conflict exists in the brief as written. ADR 0005 proposes containment. If the strict reading is intended, RL-M3-004 becomes fixed per-framework pipelines and the product is materially smaller.
    R-03 Front-end framework chosen without knowing the team ● closed 2026-08-02 human React. ADR 0001 recommended SvelteKit on runtime size and reactivity grounds; the team's daily language beat both arguments. The residual — a larger bundle on a box the operator pays for — is carried as a requirement to server-render the M1 screens where possible.
    R-04 Response timing may distinguish nonexistent from unauthorized even when status and body match ✕ open agent Body-level indistinguishability is tested byte-for-byte; timing is not. Full equalisation costs a fixed delay on every refusal. To revisit at the M5 gate as a deliberate decision rather than an assumption.
    R-05 Production and non-production sites on one host are separated by user plus systemd, not a namespace ✕ open agent, then human for the policy call The sharpest finding in the threat model. Containers are out of scope. Mitigated by warning in the interface, recommending against it in documentation, and an adversarial escape test (RL-M3-006).
    R-06 A host unreachable during authority rotation keeps trusting the old authority ✕ open agent Inherent to offline hosts. The rotation procedure must report unreachable hosts loudly and refuse to declare success. Covered by RL-M6-001.
    R-07 A compromised agent reporting false inventory would not be detected ✕ open agent No cross-checking of agent claims in v1. privd's independent root-owned audit log gives a partial cross-check for privileged operations. To revisit at the M2 gate.
    R-08 All three crown-jewel keys live on one machine ✕ open human A structural property, not a likelihood. The external key manager is a seam, not v1 scope. Mitigation candidate, not yet scoped: require second-human approval for the highest-risk operations. The gate report names this as the one it would most want ruled on before M2 hardens around it.
    R-09 Build resource contention is bounded by limits but not eliminated ✕ open agent CPUQuota and MemoryMax bound a build; page cache pressure and disk I/O are not partitioned. Mitigated by lower default build limits than runtime limits, per-host concurrency caps, and showing build load separately from application load.
    R-10 No remote repository yet ● closed 2026-08-04 human Closed on evidence: origin exists, a pull request is open against main, and CI is green on all four checking jobs for commit 18cca24. It cost five runs and every failure was a real defect — the return on an acceptance that says “runs clean in CI” rather than “runs clean locally”.
    R-11 A reverse proxy, NAT port-forward or load balancer in front of the dashboard makes it public while the C5 check reports contained ✕ open agent Detection is local by decision (ADR 0011). Mitigated by stating the blind spot in every report and in docs/NETWORK.md, not by detection. Reading the host's listening sockets for a proxy on 80/443 is a candidate, but it guesses at intent and would produce false positives on any host that also serves sites, which is most of them.
    R-12 An api_token grant can be written directly, with no intersection against the permissions of the user who issued it ▲ entry is stale agent The threat model says the ceiling “is enforced in RL-M1-032, which has not landed”. RL-M1-032 is now done, and can() evaluates the intersection on every decision. The mechanism exists; the register entry was not updated.
    R-13 A disabled user's grants still resolve to allow ● answered in can() agent Recorded so the omission does not read as an oversight: “may this actor act at all” is one question per request, not one per hierarchy node, so users.disabled_at belongs in can() rather than in grant resolution. It is step 3.
    R-14 Managed databases change the product's failure story ✕ open — highest impact in the register human Every workload Ratline manages today is reconstructible; a site comes back from git. A database does not. Adding managed databases moves the product from “if it breaks, redeploy” to “if it breaks, the company may have lost its data”, and two accepted decisions — ADR 0009 (build on the target host) and ADR 0005 (build commands contained, not eliminated) — both put user-authored code next to the data. M7 is ordered so backup and verified restore land before create and delete are exposed.
    R-15 The sign-in path derives a 128 MiB scrypt hash per attempt, including for accounts that do not exist ▲ open; entry partly stale agent Deriving unconditionally is correct — it is what stops timing revealing whether an account exists. Memory is bounded by the libuv threadpool width; what is unbounded is the queue of pending derivations, so it is an availability lever more than a memory-exhaustion one. The entry says “nothing calls the limiter — there is no HTTP layer”; RL-M1-042 has since bound the server, and RL-M1-020 is still in review because two of its four authentication paths have no endpoints yet.
    R-16 The constant-time password comparison is enforced structurally, not behaviourally ✕ open agent No functional test can distinguish secretEquals from === or Buffer.equals: all three accept the same passwords and differ only in rejection timing. A source-level assertion catches the mutation someone actually makes; it does not catch every possible one, and says so.
    R-17 An administrative password reset is an account transfer ▲ rewritten, residual accepted agent Between the reset and the member's next sign-in, the operator holds a working credential for somebody else, and every action taken with it is attributed to that person. Closed as far as a password alone permits: member.reset_password is Owner and Admin only, the reset is audited against the operator before the credential can be used, and every session the member held is revoked so they notice. The residual — the impersonation window — cannot be closed by any arrangement of the reset.
    R-18 Rate-limit counters are tenant-scoped, so an attacker who knows N organization ids gets N address budgets ✕ open agent Forced by row-level security and the non-nullable org_id rule; an untenanted table would need a second, unscoped data-access primitive, which C3 forbids. Small on a self-hosted install, real.
    R-19 Per-account rate limiting is itself a denial of service against a named account ✕ open agent Inherent to per-account limiting. The window is fixed rather than sliding so it releases on time, and a proven success clears it — neither release needs an administrator.
    R-20 The limiter's own overload mode is row-lock contention, pool exhaustion, then a fail-closed refusal for everyone ✕ open agent Bounded, loud and self-healing, traded deliberately against an unbounded memory failure. The fix if the ceiling is reached is admission control in front of the auth handlers, not a larger limit.
    R-21 The address dimension is only as strong as the derivation of the source address ✕ open agent Trusting a forwarded-for header from an untrusted hop makes evasion free and lets an attacker exhaust someone else's budget. The single easiest way to make the rate limiter decorative. Owed by whatever builds the HTTP layer.
    R-22 The CSRF token is derived from the session id, so it is constant for the life of a session ✕ open agent A token that escapes — into an access log, a Referer, a crash report — stays valid until the session ends. Per-request tokens need server state whose only purpose is to be kept in step with the session, which is the synchronisation nobody maintains. Mitigated by keeping the token out of cookies and URLs entirely, refusing one presented in a query string rather than ignoring it, and by an absolute, short session lifetime. Not eliminated.
    R-23 Nothing calls the CSRF guard ● closed by RL-M1-042 agent createServer runs guardCsrf on every unsafe method, and the authorization matrix drives real POSTs through it — a request without a token is refused, which the matrix caught the first time by failing three cells.
    R-24 An abandoned but open browser tab keeps a usable session for up to the absolute lifetime ▲ deliberate agent Not an omission. An idle timeout measured on last_seen_at records the last request, not the last human: a dashboard polling for deploy status writes it on a timer, so the rule would fire only when the tab is closed — which the absolute lifetime already covers — and never for the abandoned open tab, which is the whole scenario. Mitigated by the eight-hour absolute lifetime, made shortenable per organization; the operating system's screen lock, stated plainly in the interface; and re-authentication for the highest-risk actions, which polling does not defeat. Two-factor does not mitigate it — the walked-away case has already passed both factors.
    R-25 The TOTP shared secret is a symmetric credential the control plane can impersonate its holder with ✕ open agent Inherent to TOTP; the scheme that removes it is WebAuthn, where the verifier stores only a public key. Mitigated by envelope encryption, so the database alone is not enough, and by the key file being excluded from database backups. Scoped out rather than overlooked.
    R-26 An administrative reset of a second factor removes the bound that makes R-17 survivable ▲ capability closed, residual accepted agent Whoever holds both resets can take an account outright. Bounded the same three ways as R-17, and the two actions are deliberately held by the same roles with a test asserting they move together — splitting them would suggest the pair is safer than either, and it is the opposite. The residual is the pair itself, which no arrangement of either action can close: it is the definition of an administrator.
    R-27 Beginning a re-enrolment makes the existing enrolment pending, so somebody holding a stolen session can strip a victim's second factor ✕ open agent Bounded: the attacker already holds a session that passed the factor, so it costs the victim a re-enrolment rather than access, and a password-only challenge cannot do it at all — that path is refused outright. Closing it means staging the new secret beside the old one, which is two more columns; named in migration 12 so the omission reads as a decision.
    R-28 Two-factor verification is not rate limited in effect ● closed agent POST /auth/two-factor spends its budget before it verifies anything, proven by a test that drives the endpoint past its limit and reads the counter. The bucket keys on the challenge token, and a fresh challenge cannot buy fresh attempts, because minting one requires a successful sign-in and sign-in is limited on the account and the address — so the two budgets multiply.
    R-29 Repository reads that resolved no permission at all ● closed by RL-M1-043 agent Row-level security still confined all of them to one tenant, so it was a within-tenant privilege gap rather than a cross-tenant one, and nothing called them over HTTP because there was no server. The durable fix is test/security/repository_gating.test.ts: every exported repository function resolves a permission or carries a written argument for why not. The count differs between documents — see the defects page.
    R-30 Only a minority of matrix cells are verified end to end ▲ accepted; entry has stale numbers agent Not a defect, and reported as a number rather than a caveat. The remainder is verified against can() with real grants and forced row-level security, which proves the permission model and not that a route consults it. Every route gains transport coverage as its repository function is written. The entry says “56 of 567 cells” and “8 of 27 declared routes”; the generated metrics say 630 cells and 12 of 30 routes.

    Threat model diff at the M1 gate

    R-22 through R-30 were added. R-01, R-03, R-10 and R-23 closed. R-17 and R-26 were rewritten rather than closed, because an administrative password or second-factor reset is an account transfer and the residual is the pair itself, which no arrangement of either action can close. Still open and the owner's: R-02, R-05, R-08 and R-14.
