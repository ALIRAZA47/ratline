ratline / workflow

    Development workflow

    The tracking artifacts are treated as production code: they are reviewed, they are kept accurate, and a milestone with a stale tracker is not done. The CLI exists so that tracking is mechanical rather than a chore, and it refuses things rather than reminding people.

    The tracking system

    docs/tasks.yaml is the source of truth for all work. Every unit of work exists there before it is worked on. Task ids are immutable and never reused, in the form RL-<milestone>-<3-digit sequence>.

    The Definition of Ready

    A task cannot enter in-progress unless every depends_on is done and it has at least one acceptance line. XL is not a valid resting state — split it before starting. A dropped task is never deleted: set status: dropped and add a note explaining why.

    The security rule

    Any task touching authorization, secrets, remote execution or TLS is risk: high and requires a matching entry in the security test suite before it can go to done. The dashboard lists high-risk tasks that name no security artifact, so the rule is visible rather than remembered.

    The CLI

    Zero dependencies and no build step. Node 22.6 or later runs the TypeScript directly by type stripping, so the tracker works on a stock Node with nothing installed. The wrapper script finds a suitable Node and gets out of the way.

    Subcommands of ./scripts/tasks
    CommandWhat it does
    tasks listFilter by --milestone, --status, --owner, --risk, or emit --json
    tasks nextTasks whose dependencies are met
    tasks addCreate a task with a milestone, title, estimate, risk and owner
    tasks startEnforces the Definition of Ready, sets status, stamps time
    tasks checkMark acceptance line n met, or --uncheck it
    tasks noteAppend a dated note
    tasks reviewBuilt and locally verified; needs outside confirmation
    tasks blockAlso writes docs/RISKS.md
    tasks unblockWith an optional reason and target status
    tasks doneRequires every acceptance line met and green CI. --no-ci "<reason>" records why the gate was bypassed
    tasks sync-blocksDerives blocks from depends_on, because maintaining both by hand does not survive 181 tasks
    tasks validateSchema, enums, id format, dangling references, depends_on/blocks symmetry, dependency cycles, and the brief's own rules. Runs in CI.
    tasks renderRegenerates docs/STATUS.md. --check fails if it is stale

    Two schema additions were made because the brief's rules could not otherwise be enforced: acceptance_met, holding the indices of satisfied acceptance lines so done can actually refuse; and tasks sync-blocks.

    The other two artifacts

    docs/STATUS.md
    Generated, never hand-edited. Milestone progress, the current milestone and which exit criteria are met, everything in progress and blocked with age in days, open high-risk tasks not covered by a security test, test health, and the count of open critical and high security findings — a number that must be zero at every gate.
    docs/PROGRESS.md
    Append-only session log, newest entry at top, never edited afterwards. Each entry records the goal, what completed, what is in progress, what is blocked, decisions made, surprises, deviations from the brief, and what the next session should start with.

    The session protocol is fixed at both ends. Before writing any code: read STATUS.md, the top three PROGRESS.md entries and the tracker filtered to in-progress and blocked; run tasks validate and the full test suite; report anything already red before touching it. At the end: update the tracker, append the log entry, re-render the dashboard, and commit the tracking updates as their own commit.

    Running it locally

    Node 22.6 or later is required and .node-version pins it. The code runs TypeScript directly through type stripping, so most of the tree has no build step; the exception is the React front end, because JSX is not erasable, and Vite covers that alone.

    A project-local Postgres

    The development cluster lives inside .ratline/pgdata on port 55432, so it neither collides with nor disturbs whatever Postgres is already on the machine, and the whole thing is disposable.

    ./scripts/pg start        # initdb if needed, then run
./scripts/pg psql         # a shell on it
./scripts/pg reset        # throw the cluster away and rebuild

./scripts/migrate up      # apply migrations
./scripts/migrate cycle   # up, down, up — the gate a new migration must pass

    cycle is the interesting one. Asserting that a down path exists is a parser check; only the second up reveals a rollback that dropped the wrong object or left something behind. CI runs it as its own job against a real Postgres 17, because §9 forbids mocking the thing under test and a migration runner tested against a fake proves nothing about whether the SQL applies.

    Checking a host before serving anything

    ./scripts/preflight          # generates secrets on first run; refuses on
                             # anything missing, weak or publicly bound

    That is C4 and C5 in one command: it generates the three secrets — cookie, key-encryption key, instruction signing — on first run, refuses to proceed if one is missing, weak, truncated or readable by other users on the host, and classifies the bind address, refusing an exposed one without an explicit acknowledgement.

    A real Debian host in a container

    §6.7 rules out mocks for anything that touches a host. ./scripts/host brings up a real one reproducibly, so a test run does not depend on a pile of Docker flags somebody remembered:

    ./scripts/host start      # build if needed, run, wait for sshd, print the port
./scripts/host verify     # assert the three things R-01 actually requires
./scripts/host ssh        # a shell as the bootstrap account
./scripts/host stop

    The container needs --privileged and a writable cgroup mount because it runs systemd as PID 1, and the script supplies both. verify asserts that SSH accepts the non-root deployer account with working sudo -n, that systemctl is-system-running returns running rather than degraded, and that root SSH is refused — by the image's default rather than by a test arranging it.

    One vacuous pass, caught in the verifier itself

    It first reported “root ssh: refused (C1 holds)” on a machine with no key file — passing because it could not connect at all. It now refuses to conclude anything until the deployer connection works. Recorded in R-01 rather than quietly fixed, because it is the same class of failure as a test suite that passes while exercising nothing.

    The agent binaries

    ./scripts/agent build [version]   # both binaries, both architectures
./scripts/agent verify            # everything CI checks, in CI's order
./scripts/agent test              # go test ./... on its own

    Two binaries because the agent is unprivileged and ratline-privd is the root helper that distrusts it. Two architectures because an arm64 host is a normal thing to manage, and a build that only ever ran on amd64 discovers its cgo dependency on somebody else's server. verify is gofmt, go vet, go test, and a reproducibility check that builds the same tree twice and compares the bytes — which is the claim the checksum-before-execute bootstrap depends on.

    Everything CI runs

    npm run check    # lint, typecheck, test, tasks validate

    The CI pipeline

    Five jobs. Four of them check something; the fifth records the result and runs only if all four succeeded.

    The five jobs in .github/workflows/ci.yml
    JobWhat it runsWhy it is separate
    Tracker ./scripts/tasks validate and ./scripts/tasks render --check A malformed tracker fails the build on its own merits, and a red test suite must not hide a stale dashboard or vice versa. --check compares only the tracker-derived sections, because test health and build status legitimately change every run.
    Lint, typecheck, test npm run lint, npm run typecheck, ./scripts/ci-metrics, against a real Postgres 17 service Writes .ratline/metrics.json and .ratline/security-findings.json, which the dashboard reports, and exits non-zero if any test failed.
    Migrations up, down, up ./scripts/migrate cycle, then ./scripts/ci-metrics --integration A real Postgres, not a mock. Integration tests run here rather than in the code job.
    Agent binaries ./scripts/gen-agent-protocol --check, ./scripts/agent verify, then a release build with checksums The drift check is what makes “the two sides cannot disagree” true rather than promised. A stale generated catalogue would mean the control plane signs instructions the agent refuses, which presents as a broken host rather than as a stale file.
    Record CI status Writes .ratline/ci-status.json tasks done refuses to close a task unless this file reports green, and it is written only when all four jobs above succeeded. Nothing outside CI writes it — a local run that minted its own green light would defeat the gate.
    Two configuration choices that look wrong and are not

    Postgres runs with POSTGRES_HOST_AUTH_METHOD: trust. The fixtures connect as ratline_app, which migration 2 creates NOLOGIN and passwordless deliberately — a login role with a shipped password is the default credential C4 forbids. Giving the role a password for CI only would make the pipeline test a configuration production never uses. It is safe here in a way it would not be anywhere else: an ephemeral container, on loopback, inside one job, destroyed with it.

    The workflow triggers on push only. A pull_request trigger alongside it meant every push to a branch with an open PR started two full pipelines, because github.ref differs between the events so the concurrency group does not collapse them and neither cancels the other. The comment in the workflow says plainly what to restore it for: a fork's pull request would otherwise arrive with no CI at all, and unlike the merge-result question, that gap is silent.

    The DATABASE_URL is set in CI on purpose, because skipping is the dangerous shape rather than failing. The test support layer skips database suites only when the variable is unset and throws when it is set and unreachable — so a pipeline cannot report a green security suite that never touched a database. The first run of the workflow proved what that costs: 320 of 592 tests passed, the authorization matrix reported that it had not run and was therefore unknown rather than green, and both coverage gates refused at 71%. The gates were right and the workflow was wrong.

    Gates that fail on absent coverage

    Two coverage gates, and nothing else is gated. A blanket coverage target buys percentage-chasing on code that does not need it:

    The two coverage gates in scripts/ci-metrics.ts
    GateRequiredCurrent
    can() branch coverage100%100%
    src/authz/** line coverage100%100%

    A gate whose value is null fails. “Not measured” is a failure, not a pass — because otherwise renaming a file, or breaking coverage collection, would switch the gate off silently, which is the failure mode the gate exists to prevent. That has already happened once for a different reason: a change to the coverage event shape made the collection branch unreachable, both gates reported “not measured”, and the build failed for a reason that had nothing to do with coverage. The type checker caught it.

    The same principle runs through the metrics collector. The authorization matrix writes its own report file on every run, and a missing report means the matrix did not execute — reported as unknown rather than as green. There is no arrangement under which yesterday's green matrix is reported as today's. Failures are recorded by name and not merely counted, because the first two CI failures were undiagnosable without local reproduction when only counts were written.

    A known hole in the coverage gate

    RL-M1-051 (todo) — “Fail the coverage gate for an authz file no test ever loads”. A file inside src/authz/ that no test imports contributes nothing to the aggregate rather than dragging it down, so the current gate would not notice it.

    Mutation testing as a practice, not a tool

    Every security-critical change in M1 was mutation-tested by hand: a property was broken deliberately, the resulting failure confirmed, and the source restored from a copy. There is no mutation-testing dependency — this is a discipline, applied per change.

    The part worth copying is what happens when a mutation escapes. Three did, and each is recorded rather than omitted, because each exposed a test asserting the right thing for the wrong reason. One of those cases is written up as a residual risk in its own right: no functional test can distinguish a constant-time comparison from === or Buffer.equals, because all three accept the same passwords and differ only in rejection timing — so the assertion is made at source level, and it catches the mutation someone actually makes rather than every possible one, and says so.

    The sentence the M1 gate report draws from all of this

    A test suite measures correctness, not its own health. Four defects in M1 were invisible while every test was green, and all four were found by timing or stress rather than by running. What they were.

    Commit and branch conventions

    • Branch per task: m2/RL-M2-014-caddy-vhost-templating.
    • Commit subject: RL-M2-014: generate caddy vhost from template with escaped values.
    • Every commit references exactly one task id. No mixed commits.
    • The commit body includes the Acceptance: lines checked off, and Risk: for high-risk tasks.
    • Never commit directly to main. Never force-push a reviewed branch.
    • Tracking updates are their own commit: chore(tracking): session 7.
    • Every dependency added requires a one-line justification in the commit body, and the standard library is preferred. The three font packages carry theirs in src/web/lib/design/fonts.ts.

    M0 deviated from branch-per-task deliberately and said so: twenty-six local branches with no remote and no reviewer is ceremony rather than review, so M0 used one branch and resumed branch-per-task at M1, when there was code, a remote and something to review against.
