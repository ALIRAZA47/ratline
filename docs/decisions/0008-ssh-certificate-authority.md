# 0008 — SSH certificate authority design

**Status:** proposed
**Date:** 2026-08-01
**Task:** RL-M0-017

## Context

§6.4 makes managed SSH part of the product: short-lived certificates instead of
`authorized_keys` entries, principals derived from grants so the host and the
interface cannot disagree, per-site Linux users, scoped sudo, a recorded web
terminal, and a documented story for the certificate authority key.

The failure mode being designed against is the ordinary one: a contractor
leaves, someone removes them in the panel, and their key stays in an
`authorized_keys` file on a host that was unreachable that afternoon. The panel
says revoked; the host says welcome. Certificates fix this by making access
expire by default rather than persist by default.

## Options considered

### Access mechanism

| Option | Assessment |
| --- | --- |
| Managed `authorized_keys` files | Revocation is a push to every host, and it fails silently on any host that is down. The UI and reality diverge exactly when it matters. Rejected. |
| Short-lived user certificates signed by an internal authority | Access expires on its own. A host that never hears about a revocation still stops honouring the certificate. **Chosen** — and what the brief specifies. |

### Where the authority key lives

| Option | Assessment |
| --- | --- |
| On disk beside the application, restrictive mode | Simple; same posture as the secret-wrapping key. **Chosen for v1.** |
| Hardware token or external key manager | Correct for larger installations. **Seam, documented, not implemented in v1.** |

### Revocation

| Option | Assessment |
| --- | --- |
| Short lifetime only | New sessions stop within the lifetime, but an established session persists. Insufficient — the M6 exit criteria require killing active sessions. |
| Short lifetime plus a revocation list plus active session termination | Meets the exit criteria. **Chosen.** |

## Decision

**Certificates.** Users upload public keys; Ratline never handles a private key.
On request, the authority issues a certificate with a default eight-hour
lifetime, configurable per organization, carrying principals derived from the
requester's *current* grants at issue time.

**Principals are the join between the model and the host.** A principal encodes
the scope it came from, following the site user convention — a grant on site
`marketing-www` yields principal `rl-marketing-www`. Hosts authorise via
`AuthorizedPrincipalsFile`, generated by `privd` from the same grant data the
interface renders. The host and the interface cannot disagree because neither
holds an independent copy of the policy; both are projections of the grant
table. A user with no grant receives no certificate rather than one with an
empty principal list, because an empty list is easy to mis-handle into meaning
"any".

**Revocation is three mechanisms together:**

1. Short lifetime — the default state is expiring.
2. A key revocation list distributed to hosts and consulted by `sshd`, so a
   revoked certificate stops working before it expires.
3. Active session termination — revoking a grant signals the agent to terminate
   sessions belonging to that principal.

The M6 exit criterion is explicit: revoking a grant blocks new sessions
immediately and kills active ones within the certificate lifetime. All three are
needed to hit it.

**Scoped sudo.** `sudoers.d` fragments are generated per role and per site,
listing fully-qualified commands with no wildcards — restart *this* unit, tail
*this* log. Every fragment passes `visudo -c` before installation, and a failure
aborts without touching live policy. Fragments are fuzzed over site and service
names (RL-M6-004), because a name that escapes the fragment grammar is a
privilege escalation, not a formatting bug.

**Web terminal.** Its own permission, off by default for every role except
Infrastructure. Sessions are recorded in asciicast format, retained per policy,
viewable from the audit log, and the recording itself is permission gated — a
recording of a production incident contains everything typed and printed,
including anything an operator pasted.

**Key hygiene.** Fingerprint, age and last use are shown per key. Organizations
can enforce a minimum algorithm strength and force rotation.

## Consequences

**Makes easy.** Time-bound and incident access, because expiry is the default
rather than a cleanup job. Answering "who could reach this host last Tuesday",
because certificates are issued records.

**Makes hard.** Operators who are used to `ssh-copy-id` need a client-side
step to fetch a certificate. Mitigation: `rl ssh <site>` in the CLI does the
fetch and the connection in one command, and the manual path is documented.

**What we live with.** A certificate valid for eight hours cannot be un-issued
except through the revocation list. If a laptop is stolen at hour one, the
window is real. Shorter lifetimes narrow it at the cost of more re-issuance;
eight hours is the brief's default and the right starting point.

**New attack surface — the authority key is the crown jewel.** Holding it means
minting a certificate with any principal for any host, which is shell access as
any site user across the entire fleet. It is strictly more dangerous than the
instruction signing key, because that key is confined to the enumerated
operation catalogue while this one grants a shell.

Storage, rotation and compromise recovery are documented in
`docs/THREAT-MODEL.md`. Compromise recovery, in outline: generate a new
authority, distribute the new trusted-authority file to every host, remove the
old, and revoke every outstanding certificate. Any host unreachable during that
process still trusts the compromised authority — which is why the procedure must
be tested and the set of unreachable hosts must be reported loudly rather than
skipped.
