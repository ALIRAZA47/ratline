# 0018 — Two-factor authentication

**Status:** proposed
**Date:** 2026-08-02
**Task:** RL-M1-019

## Context

Brief §6.3 requires two-factor authentication with an organization-level policy.
RL-M1-019's acceptance adds three specifics: TOTP enrolment producing recovery
codes, an organization able to *require* it with non-compliant members forced
into enrolment at next login, and recovery codes that are single-use and whose
consumption is audited.

The implementation was delegated and is recorded here because the decisions it
made are architectural and were argued in module headers rather than in a
decision record. Comparable work proposed ADR 0015 (rate limiting) and ADR 0016
(CSRF); this closes the gap.

## Options considered

### What a person holds when they owe a second factor

This is the decision everything else follows from.

| Option | Assessment |
| --- | --- |
| A session row flagged `pending_second_factor` | Every existing reader of `sessions` becomes wrong *by omission*: `validateSession`, `listOwnSessions`, `revokeSessionsOfUser` and the CSRF token derivation all treat a row as a session. Each would need a clause, and the one that forgot would fail open. Rejected. |
| **No session at all — a separate five-minute single-use challenge** | Nothing that reads `sessions` changes meaning. **Chosen.** |

The chosen form has a second property worth naming: the challenge is returned
from `signIn` as `ok: false`. Every caller written before two-factor existed
branches on `result.ok`, so it refuses the sign-in rather than proceeding
without a session. A new field on the success arm would have been ignored by
exactly those callers, which is the same failure the flagged-session option has,
one layer up.

### TOTP or WebAuthn

TOTP. WebAuthn is strictly better — the verifier stores only a public key, so a
compromised control plane cannot impersonate anybody — and it is a larger piece
of work with a browser dependency, on a product that does not yet have an HTTP
layer. The residual is recorded as **R-25** rather than left implicit: the TOTP
shared secret is symmetric, so whoever holds both the database and the
key-encryption key file can mint codes for anyone.

### How the secret is stored

Envelope-encrypted per ADR 0006, with the key-encryption key a **required
parameter** rather than a lazy filesystem load — so a caller cannot obtain a
usable secret without having deliberately supplied the key.

The shape is enforced by a CHECK constraint (`v1$<wrapped key>$<sealed secret>`,
both base64url). A bare base32 secret cannot satisfy the pattern, which makes
storing one a **constraint violation rather than a review finding**. That is the
same move migration 10 makes for session tokens, applied to a different encoding.

### Recovery codes

SHA-256 digests, not a password hash: a recovery code is high-entropy and
generated by us, so the slow-hash argument that applies to a human-chosen
password does not apply. Single use is one guarded `UPDATE` with `used_at is
null` in the predicate, so two concurrent redemptions cannot both win.

### Replay

A monotonic `last_used_step`. RFC 6238 tolerates clock skew by accepting a
window of steps, which means a code observed in transit is valid for up to ninety
seconds; recording the highest counter used and refusing anything at or below it
closes that without also refusing a legitimate retry.

### No dependency

RFC 4226 §5.3 dynamic truncation and RFC 4648 §6 base32 are written out against
`node:crypto` and checked against the RFCs' own test vectors. Brief §6.7 prefers
the standard library and requires a written justification for any dependency; a
TOTP library is roughly this much code plus a supply chain.

## Decision

As above: a challenge rather than a partial session, TOTP with the WebAuthn gap
recorded, envelope-encrypted secrets with the shape enforced in the database,
digest-hashed single-use recovery codes, monotonic replay protection, and no new
dependency.

## Consequences

- Enrolments are per `(organization, person)`, forced by the non-nullable
  `org_id` invariant every table in this schema carries. Somebody in three
  organizations enrols three times. Argued in migration 12; a reviewer may
  reasonably disagree, and changing it means changing that invariant, not this
  feature.
- **There is no administrative reset of a second factor** (R-26). It is the most
  dangerous capability in the feature — it turns off anybody's second factor —
  and the catalogue has no action to check an administrator against. Shipping it
  with the check "to follow" is what §9 rejects. This is the same answer
  `updatePasswordHash` gave before RL-M1-034 catalogued
  `member.reset_password`, and it wants the same treatment.
- Beginning a re-enrolment makes the existing one pending, so abandoning it
  leaves the person without a factor (R-27). Bounded: it needs a full session,
  never a challenge. Closing it costs two staging columns.
- **Verification is not rate limited in effect** (R-28). `AUTH_RATE_LIMITS["two-factor"]`
  publishes a budget and nothing spends it, because the limiter must run before
  the work and that ordering belongs to a route handler that does not exist. A
  six-digit code is a million possibilities; an unlimited verifier finds one
  inside a day. **This is the sharpest open item in the feature** and it is owed
  by whoever builds `src/api/`.

## What is NOT done

- WebAuthn, SMS, or email codes.
- Administrative reset (needs a catalogued action first).
- Trusted-device / "remember this browser" suppression.
- Any wiring to an HTTP layer, which does not exist.
