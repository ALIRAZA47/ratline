## What was built

The control plane, and the security model everything downstream hangs off.

- **One authorization decision, at the data layer.** `can()` with 100% branch
  coverage, enforced by a gate that treats *absent* coverage as failure — so
  renaming the file cannot switch off its own check. No route handler calls it.
- **No authorization middleware, deliberately.** §9 forbids a check "in addition
  to" the data layer. That reading, ruled on by the owner, immediately found
  **nine repository reads that resolved no permission at all**, including the
  audit log — every member of a tenant could read the whole of it. A middleware
  would have masked all nine and left the repositories exactly as wrong.
- **An authorization matrix of 630 cells** — every role × every endpoint × own /
  other-tenant / nonexistent — generated from the route table, so an endpoint
  without coverage fails the build. It reports *which layer* verified each cell:
  56 through real HTTP requests, 448 against `can()` with real grants and RLS,
  126 unguarded routes checked structurally. A single pass rate would have hidden
  that distinction, and the distinction is the honest part.
- **Tenant isolation in three layers that fail closed independently:** a database
  handle unreachable outside `src/repo/`, a branded context no other module can
  construct, and forced row-level security. Every isolation test connects as the
  unprivileged role, because a superuser bypasses policies and the tests would
  otherwise pass while exercising nothing.
- **Hash-chained audit log** with a separate truncation watermark, because a
  chain cannot detect removal of its own head.
- Sessions with rotation, two-factor with recovery codes, CSRF bound to the
  session, rate limiting spent *before* the expensive work, administrative
  password and second-factor resets, re-authentication for the riskiest actions,
  and first-run installation claiming.
- **598 tests**, ~75s, both coverage gates at 100%. Every security suite runs
  against a real Postgres; §6.7 rules out mocks for anything touching a host.

## What I chose to do differently, and why

**Refusals are one frozen constant, not two matching code paths.** §6.3 asks that
unauthorized and nonexistent be indistinguishable. Two paths that produce the
same bytes today are two paths, and one grows a helpful message. `refuse()`
returns the response *and* the audit record together, so the refusal cannot be
obtained without recording what really happened.

**First-run claiming is gated by a token on the filesystem, not by an empty
database.** The obvious gate is unavailable *because* C3 works: a bound context
cannot see whether any other organization exists, and reaching around it needs a
`SECURITY DEFINER` function counting rows the application must not see. The token
makes the authority **host access rather than network access**, which is the
right authority, and it handles the case the empty-database gate gets wrong in
the dangerous direction — a database that is not empty but was never claimed.

**No session idle timeout** (ADR 0017). An idle rule measured on `last_seen_at`
records the last *request*, not the last human; a polling dashboard writes it on
a timer, so it would fire only when the tab closes — which the absolute lifetime
already covers — and never for the abandoned open tab, which is the entire
scenario. Shipping it would be worse than its absence, because an operator who
believes the console signs itself out locks their screen less often.

**React, not SvelteKit** — your ruling. It has a consequence ADR 0001 did not
anticipate: JSX is not erasable, so `node --experimental-strip-types` refuses a
`.tsx` file and Vite became the project's first build step. Paid for by keeping
everything decidable in `.ts` — the rail, breadcrumb, chip, tension states,
palette and audit view model are all data, and the components only arrange them.

**Transport coverage is 56 of 630 cells.** Eight of 27 routes are bound; a route
with no repository function behind it is deliberately *absent* rather than
stubbed, because a stub answers everybody identically and reports itself as
guarded. Recorded as R-30.

**Four defects that were invisible while every test was green**, all found by
timing or stress rather than by running:

1. A scratch-database name derived from a boot-shared clock collided across
   processes, and `with (force)` turned that collision into terminated
   connections mid-test. Two individually correct decisions, jointly a landmine.
2. Twelve suites passed locally on cluster state an early session left behind —
   `alter role ... login` is persistent. Only a fresh CI database could notice.
3. A 20x "regression" I reported from one sample, which four timed runs showed
   did not exist; both slow measurements were taken while orphaned processes from
   my own killed commands hammered the same database.
4. `ci-metrics` reported counts and not names, so the first two CI failures were
   undiagnosable without local reproduction.

The pattern is worth stating plainly: **a test suite measures correctness, not
its own health.**

## Security posture

**Threat model diff since M0:** R-22 through R-30 added. R-01, R-03, R-10 and
R-23 closed. R-17 and R-26 rewritten rather than closed — an administrative
password or second-factor reset is an *account transfer*, and the residual is the
pair itself, which no arrangement of either action can close. It is the
definition of an administrator.

**R-28 closed:** two-factor verification is rate limited in effect. The bucket
keys on the challenge token, and a fresh challenge cannot buy fresh attempts,
because minting one requires a successful sign-in and sign-in is limited on the
account and the address — the budgets multiply.

**Still open and yours:** R-02 (C2 versus user-authored build commands), R-05
(production and non-production co-located), R-08 (all three crown-jewel keys on
one machine), R-14 (managed databases change the failure story). R-08 is the one
I would want a decision on before M2 hardens around it.

**Candour warning.** `docs/THREAT-MODEL.md` names the crown jewels and states
plainly that concentrating all three on the control plane is the biggest
structural risk in the design. That is what a threat model should do. It is also
a roadmap for anyone attacking a real deployment, and the repository is now
public. Worth a deliberate decision rather than a default.

## Recommended next milestone scope adjustment

**Bind more routes before adding features.** Transport coverage is 56 of 630
cells because only eight routes have repository functions behind them. Every
route bound raises real end-to-end coverage, and the matrix already demands it —
this is cheap, mechanical, and worth more than it looks, because the decision
layer proves the permission model while the transport layer proves a route
consults it.
