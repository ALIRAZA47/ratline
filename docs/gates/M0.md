## What was built

The tracking system, working rather than described. `docs/tasks.yaml` holds 143
work items covering M0 through M3 in detail with M4 through M6 outlined, each
with acceptance criteria and dependencies. `scripts/tasks.ts` is a
dependency-free CLI that enforces the brief's rules mechanically: it refuses to
start a task whose dependencies are unfinished or that has no acceptance
criteria, refuses to close one until every acceptance line is checked off,
refuses to close a security-relevant task that names no security test, and
refuses to close anything without green CI unless you record a reason. It runs
on a stock Node 22 with nothing installed. `validate` checks the schema, the
dependency graph, cycles and the brief's own rules, and fails the build in CI.
`render` generates `STATUS.md`, which is never hand-edited.

The plan itself covers the architecture and its privilege levels, a data model
through M6, every trust boundary with the test that proves it, a threat model
answering the three required compromise scenarios, and a design plan. Ten
decision records carry the reasoning, including three places where I disagree
with the brief and one where two of the brief's own requirements conflict.

## What I chose to do differently from the brief, and why

**Three departures from the suggested stack**, each argued in ADR 0001:

- **Postgres for the queue, not Redis** (ADR 0007). Peak realistic throughput is
  tens of jobs per second; Postgres handles thousands. Redis would be a second
  stateful service for every self-hosting operator to install, secure, patch and
  back up, for headroom we will never use. It also lets a deploy job be enqueued
  in the same transaction as the deployment row, removing a class of bug.
- **Hono, not NestJS.** NestJS's guard-and-interceptor culture pushes
  authorization into the route layer — the §9 anti-pattern that C3 exists to
  prevent. Its DI graph also makes "what can reach the database?" harder to
  answer statically, which is the question the C3 lint rule must answer.
- **Node 22 LTS, not Bun,** for the control plane. Ratline supports Bun as a
  deployment target, but the control plane holds the fleet's signing key and its
  security-update cadence matters more than throughput. The brief itself cites
  Bun's temp-directory handling breaking under `ProtectSystem=strict`.

**A design decision the brief leaves open.** The brief says colour must be
readable at a glance and asks for a committed status colour language. I took
that further: **Ratline has no brand accent colour at all.** Every saturated hue
carries operational meaning, so red is always failure and never a button. The
brand lives in warm neutrals, linework and type. This costs the marketing
palette and buys an interface where colour is signal.

**Three process deviations:**

1. **One branch for M0 (`m0/plan`), not one per task.** Twenty-six local branches
   with no remote and no reviewer is ceremony, not review. Branch-per-task
   resumes at M1, when there is code, a remote and something to review against.
   `main` holds only an empty bootstrap commit. Commits are one per task ID as
   the brief requires, with two exceptions where several tracked tasks produced a
   single file — the CLI (RL-M0-004 with 005, 006, 007) and the backlog
   (RL-M0-024 with 003). Those commits name the primary task in the subject and
   list the others in the body rather than pretending to a split that git cannot
   express.
2. **An HTML comment at the top of `BRIEF.md`** recording that only you amend it.
   It renders as nothing, so the document is verbatim as read.
3. **Design-record tasks are `risk: medium`, not `high`.** The high rating gates
   on the existence of a security test, which a document cannot have; rating them
   high would have made them permanently un-closable. Their implementation
   counterparts in M1 and M2 carry `high`. Flagging it because it looks like
   rule-bending and I would rather you judge it than not see it.

**Two additions to the tracker schema**, both because the brief's rules could
not otherwise be enforced: `acceptance_met` (1-based indices of satisfied
acceptance lines, so `done` can refuse) and `tasks sync-blocks` (derives `blocks`
from `depends_on`, because maintaining both by hand across 143 tasks is exactly
how a tracker goes stale).

## Security posture

**New attack surface introduced this milestone:** none. No code, no
dependencies, no network surface. The tracking CLI reads and writes files in the
repository and has no runtime dependencies.

**Surface designed in, to be built later:** a public agent endpoint requiring a
client certificate at the handshake (ADR 0002); the `privd` unix socket, which
is the in-host privilege boundary (ADR 0004); the build sandbox, which is an
explicit code-execution surface (ADR 0005); and three crown-jewel keys on the
control plane — SSH authority, instruction signing, secret wrapping.

**Security tests added:** 0 written, **73 specified** (53 in `test/security/`,
20 in `test/authz/`; counted from the tracker, not estimated). Every one is a named
artifact on a specific task, and `tasks done` refuses to close a `risk: high`
task that does not name one — so the coverage requirement is mechanical rather
than aspirational. They cover command injection through every field reaching a
host, path traversal in site paths and monorepo roots, cross-tenant access per
resource type, secret leakage into logs, error traces and metric labels, rate
limiting on every auth path, session fixation, CSRF, webhook replay, envelope
replay, sandbox escape, sudoers fragment fuzzing and SSH revocation.

**Open findings: 0 critical, 0 high, 0 medium.** No code to have findings in.

**Threat model diff since last gate:** first version, no diff. It ranks seven
assets, answers the three required compromise scenarios concretely, traces every
hard constraint to the failure it defends against, and lists nine residual risks
rather than hiding them.

The two findings worth your attention:

- **Control plane compromise** yields unprivileged code execution fleet-wide
  plus, via the SSH authority key, a shell as any site user. C1 means it is not
  *instant root* — but with the authority key in hand the gap narrows to a local
  privilege escalation. That is a real limit of the design, stated plainly.
- **Co-locating production and non-production sites on one host** is the sharpest
  risk. A Developer who can set a build command gets code execution as that
  site's Linux user, one sandbox boundary from production. Isolation is Linux
  users plus systemd, not namespaces, because containers are out of scope.

## What I need from you

**Blocking the M2 gate — a decision I cannot make:**

1. **Integration test hosts (R-01).** §6.7 forbids mocking anything touching a
   host, and M2 must prove a Debian 12 host provisions idempotently with zero
   root SSH. This machine has Docker but no VM tooling and no Go toolchain, and a
   container cannot faithfully exercise `ProtectSystem=strict`, cgroup limits or
   `sshd`. I need one of: cloud API credentials for ephemeral VMs (Hetzner is
   cheapest for this shape), permission to install a local VM tool, or a
   persistent test host. Per §2.10 I will not fabricate a substitute.

**Decisions that change what I build:**

2. **C2 versus user-authored build commands (R-02, ADR 0005).** This is a §2.10
   stop condition: two of the brief's requirements conflict. I propose
   containment — the command is written to a file and executed by argv as the
   site's own user in a resource-limited sandbox, with setting it as its own
   permission. If you intend the strict reading, sites get fixed per-framework
   pipelines with no editable command, and the product is materially smaller.
3. **Front end: SvelteKit or React (R-03, ADR 0001).** I recommend SvelteKit, but
   this is the weakest recommendation in the plan. If your team writes React
   daily, React is the better answer for reasons no benchmark captures. Cheap now,
   expensive after `RL-M1-028`.
4. **Second-human approval for the highest-risk operations (R-08).** Not in the
   brief and not scoped. Given that all three crown-jewel keys sit on one machine,
   requiring a second human for adding a host, installing a sudoers fragment or
   authority operations would meaningfully reduce the blast radius of control
   plane compromise. Worth adding to M5, or not — your call.
5. **Type licensing (DESIGN.md §10).** Archivo, Public Sans and JetBrains Mono
   are open-licensed and self-hostable, which C5 requires. If there is an existing
   brand or licensed family, say so now — the display face carries most of the
   personality and swapping it late is expensive.

**Resources:**

6. **GitHub organization and remote (R-10).** `ratline-dev` or `getratline` per
   §1. Until a remote exists, CI has never run, so the M0 tasks are closed with
   `--no-ci` and the reason is recorded in each task's notes.

**Review:** ADRs 0001 and 0002 are the two the exit criteria name, but **0004
(host privilege separation) and 0005 (build commands) are the ones that most
shape the security posture.** 0004 is where C1 stops being a statement about SSH
configuration and becomes a property that survives agent compromise.
